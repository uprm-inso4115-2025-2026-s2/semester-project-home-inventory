== #Operation Model#

=== #Purpose#

#This section specifies the core system operations of the Home Inventory application. An operation is a state-changing service: it receives input state variables, is performed by one responsible agent, and produces output state variables. For each operation the model distinguishes:#

* #*Domain preconditions*: descriptive conditions that make the operation meaningful in the domain.#
* #*Required preconditions*: prescriptive permission conditions that must hold before the app allows it.#
* #*Trigger conditions*: events or states that activate it.#
* #*Required postconditions*: output-state conditions that must hold after successful execution.#

#The purpose is to make implemented and planned workflows precise enough to trace to requirements, validation scenarios, and test cases.#

==== #Operation Details#

.#OP-01 -- `CreateInventoryItem`#
[cols="1,4", stripes=even]
|===
| #Field# | #Specification#

| #Performer#
| #Flutter mobile app, activated by an authenticated household member.#

| #Input variables#
| #`userId`, `householdId`, item name or barcode, category, location, quantity, optional low-stock threshold, optional expiration date, shared/personal flag.#

| #Output variables#
| #New or updated `ItemType`, `ItemInstance`, `InventoryRecord`, and optional `QuantityChangeTransaction`.#

| #Domain preconditions#
| #The household has or is acquiring an item that should be tracked. Quantity may be exact or approximate; expiration may be present or absent.#

| #Required preconditions#
| #User is authenticated and permitted to add items in the household. Required item identity fields are valid, quantity is non-negative, and shared items require shared-item update rights.#

| #Trigger conditions#
| #User taps *Add Item*, scans a barcode or enters item information, and submits the form.#

| #Required postconditions#
| #A tracked record exists for the item in exactly one household context. Provided quantity, location, threshold, expiration, and shared/personal status are preserved. The inventory list refreshes and shows the new item.#

| #Related goal / requirement#
| #N1, N2, N3; DG-REQ-01, DG-REQ-02, DG-REQ-03, DG-REQ-04; US-INV-01; IR-01, IR-04, IR-05.#

| #Related test case#
| #Proposed: `TC-OP-INV-01`. Existing overlap: `TC-TXN-01` if creation records an initial quantity transaction.#

[cols="1,4", stripes=even]
|===

| #Performer#
| #Flutter mobile app / inventory repository, activated by household member.#

| #Required postconditions#
| #Item quantity reflects the accepted change. A transaction record is appended with reason and timestamp. Low-stock and out-of-stock state are recomputed. Existing metadata remains stable unless explicitly edited.#

| #Related goal / requirement#
| #N2; DG-REQ-02, DG-REQ-03, DG-REQ-04; US-INV-02; IR-02, IR-04.#

=== #Operation-Level Consistency Rules#

#Check the following during implementation review and final documentation review:#

1. #*Unique performer rule*: every operation has one primary performer; supporting components may participate, but one agent activates the operation.#
2. #*Input/output declaration rule*: every input and output variable corresponds to a documented domain concept, database concept, UI state, or service state.#
3. #*Authorization rule*: every operation that reads or writes household-scoped data requires an authenticated user and an active household membership or equivalent personal scope.#
4. #*Non-negative quantity rule*: operations that create or update quantity must never produce a negative inventory quantity.#
5. #*Historical preservation rule*: operations that correct inventory must not silently delete spending or transaction history.#
6. #*Alert deduplication rule*: scheduled alert operations must not create duplicate alerts for the same item-condition-recipient group within the same reminder period.#
7. #*Expiration validity rule*: expiration-related operations must only run when expiration data is present and valid.#
8. #*Membership revocation rule*: once membership is revoked, the removed user must no longer access shared household inventory, shared spending, or household alerts.#
9. #*Traceability rule*: every operation traces to at least one goal, requirement, or stakeholder need and at least one existing or proposed test case.#
10. #*UI/backend agreement rule*: every user-visible operation has matching UI behavior, backend persistence behavior, and validation behavior.#
