== Manual Test Procedure

This section captures the checked-in manual procedures used to verify requirements whose verification field is *not* fully covered by automated tests in `src/test/`. Each procedure is repeatable by a reviewer who has cloned the repository, configured Supabase, and can run the Flutter client on a real or simulated device.

Manual tests live here (and not in a separate document or external tool) so the procedure is recoverable on any tagged commit and runnable without prior team knowledge.

=== When to use this procedure

* The verification field for the target requirement explicitly says "manual tests", "usability walkthrough", or "test accounts" (see Section 2.2.3 Machine Requirements and Section 2.2.2 Interface Requirements).
* No automated test in `src/test/` exercises the requirement end-to-end (cross-checked against the per-requirement coverage in Section 3.2.3).

If an automated test already covers the requirement, prefer running that test instead.

=== Setup

These prerequisites apply to every procedure in this section unless overridden.

==== Environment

* Flutter SDK ≥ 3.35.5, Dart SDK ≥ 3.9.2 (matches MR-02 supported environment).
* A dedicated Supabase *test* project (never the production project — see "Supabase integration tests (guidance)" in Section 3.2.3).
* Android emulator, iOS simulator, or two physical devices when the procedure requires multi-user synchronization.
* A wired or Wi-Fi internet connection that can be toggled at the OS level (used for offline procedures).

==== Test accounts

Create the following Supabase accounts inside the test project before running any role-scoped or shared-household procedure. Account naming uses a `test_` prefix to simplify cleanup.

[cols="1,1,2",options="header"]
|===
|Account |Role |Purpose

|`test_admin@example.com`
|Household admin
|Creates the household, invites members, exercises admin-only actions.

|`test_member@example.com`
|Member
|Default household member; exercises shared-item visibility and ordinary actions.

|`test_viewer@example.com`
|Viewer (read-only)
|Verifies that write actions are not exposed to viewers.

|`test_owner@example.com`
|Personal-item owner
|Owns a personal item that must remain hidden from `test_member` and `test_viewer`.
|===

==== Test data

Seed the test household with the following items before procedures MP-IR-09 through MP-IR-14. Quantities and expiration dates may be adjusted as long as the relative ordering is preserved.

* *Shared, in-stock*: "Charmin toilet paper", quantity 24, no expiration, low-stock threshold 6.
* *Shared, low-stock*: "Whole milk", quantity 1, expiration date = today + 5 days, low-stock threshold 2.
* *Shared, expiring*: "White bread", quantity 1, expiration date = today + 2 days.
* *Personal, owned by `test_owner`*: "Barilla gluten-free elbows", quantity 3, low-stock threshold 2.

==== Cleanup

After each session, sign in as `test_admin` and delete the test household. The cascade clears items, alerts, and grocery list entries. Auth users may require Supabase admin privileges to remove; if deletion fails, log the resource IDs so the team can clean them up out-of-band.

=== Recording results

For each procedure run, record:

* Date, reviewer name, device/OS, commit SHA of the build under test.
* Pass / fail / blocked for each step.
* For failures: actual outcome, screenshot or device log excerpt, and a link to the issue opened to track the regression.

A blank results template lives at the end of this section.

=== Procedures

==== MP-IR-09 — Role-Based Visibility and Permission Controls

*Covers*: IR-09, MR-05 (M3-QA-01, M3-QA-02). *Replaces automated test*: none. *Expected duration*: 10 minutes.

. Sign in as `test_owner`. Add the personal item "Barilla gluten-free elbows" with ownership marked *personal*.
. Sign out. Sign in as `test_member`. Open the inventory list.
+
*Expected*: "Barilla gluten-free elbows" does *not* appear in any list, search, or filter result.
. Sign out. Sign in as `test_viewer`. Open the inventory list.
+
*Expected*: The viewer sees shared items in read-only mode. Add Item, Edit Item, and Delete Item controls are either hidden or disabled with an explanatory tooltip.
. Sign out. Sign in as `test_admin`. Open the household settings.
+
*Expected*: Remove-member and change-role controls are visible. Sign in as `test_member` and confirm the same controls are *not* visible.

*Pass criteria*: All four expected outcomes hold. Any visibility leak (personal item shown to non-owner, or admin control shown to non-admin) is a fail.

==== MP-IR-10 — Filtered Inventory Lookup

*Covers*: IR-10 (M3-QA-03). *Replaces automated test*: none. *Expected duration*: 5 minutes.

. Sign in as `test_member`. Open the inventory list with the seeded test data present.
. Apply the *Stock status = LOW_STOCK* filter.
+
*Expected*: "Whole milk" appears. "Charmin toilet paper" and "White bread" do not.
. Clear the filter. Apply *Expiration status = Expiring* (items expiring within 3 days).
+
*Expected*: "White bread" appears. "Whole milk" does not (5 days out).
. Clear the filter. Search the item name "milk".
+
*Expected*: "Whole milk" appears as the only result.
. Apply *Ownership = personal*.
+
*Expected*: No items appear for `test_member` (the only personal item belongs to `test_owner`). Sign in as `test_owner` and repeat: "Barilla gluten-free elbows" appears.

*Pass criteria*: All filters narrow results correctly and clear independently.

==== MP-IR-11 — Fast Manual Entry After Barcode Failure

*Covers*: IR-11, MR-08 (M3-QA-04). *Replaces automated test*: none. *Expected duration*: 5 minutes.

. Sign in as `test_member`. Tap *Add Item* and start the barcode scanner.
. Point the camera at a piece of plain paper for at least 5 seconds, then dismiss the scanner.
+
*Expected*: The app transitions to a manual-entry form without re-prompting for the camera.
. In the manual-entry form, enter only the item name "Local pasta" and quantity 2. Leave all other fields blank. Tap *Save*.
+
*Expected*: The save succeeds and "Local pasta" appears in the inventory list immediately.
. Open "Local pasta". Edit the expiration date to a future date and save.
+
*Expected*: The expiration date is persisted on the existing record without creating a duplicate.
. Repeat step 1 with an *unrecognized* barcode (a local store-brand product whose UPC is not in the database).
+
*Expected*: The app shows an "Item not found" message and transitions to the same manual-entry fallback.

*Pass criteria*: Both the scanner-dismissed path and the unrecognized-barcode path land in manual entry with only name and quantity required.

==== MP-IR-12 — Budget Alert Preferences

*Covers*: IR-12 (M3-QA-05). *Replaces automated test*: none. *Expected duration*: 5 minutes.

. Sign in as `test_admin`. Open *Settings → Budget Alerts*.
+
*Expected*: Toggle exists for enabling budget alerts. Defaults: enabled, warning threshold 80%, exceeded threshold 100%.
. Disable budget alerts. Log a purchase that pushes spending above 80% of the active budget.
+
*Expected*: No budget alert is generated.
. Re-enable budget alerts. Log another purchase that crosses the 80% threshold.
+
*Expected*: One warning alert appears. No second alert is sent if a subsequent purchase keeps spending in the same 80–99% band (deduplication).
. Log a purchase that crosses 100%.
+
*Expected*: A second, distinct alert is sent for the 100% crossing.

*Pass criteria*: Alerts honor the enable toggle and do not duplicate within an unchanged threshold band.

==== MP-IR-13 — Shared Alert Audience and Delivery Preferences

*Covers*: IR-13, MR-07 (M3-QA-06). *Replaces automated test*: integration test in `automated_check_expiration_test.dart` exercises deduplication logic but not delivery preferences. *Expected duration*: 10 minutes (requires two devices).

. On *device A*, sign in as `test_admin`. On *device B*, sign in as `test_member`.
. On device A, set `test_member`'s notification preference to *Grouped summary* and `test_admin`'s to *Individual push*.
. On device A, change "White bread" expiration date to today (forces an Expiring → Expired transition).
. Trigger the scheduled expiration check (or wait for the next sweep).
+
*Expected*: Device A receives an individual push within one sweep cycle. Device B does *not* receive an individual push.
. Wait for the next grouped summary window (or trigger it via the settings screen).
+
*Expected*: Device B receives one grouped summary that includes "White bread" alongside any other pending alerts.
. Trigger the same sweep again without changing state.
+
*Expected*: Neither device receives a duplicate push for "White bread".

*Pass criteria*: Delivery preferences are honored independently per member, and repeated sweeps without state changes do not duplicate notifications.

==== MP-IR-14 — Restock List Override Controls

*Covers*: IR-14 (M3-QA-07). *Replaces automated test*: none. *Expected duration*: 5 minutes.

. Sign in as `test_member`. Decrease "Whole milk" quantity to 0.
+
*Expected*: "Whole milk" is auto-added to the grocery list with an indicator showing it was system-added (for example, a "Suggested" badge) and a reason ("Out of stock").
. Open the grocery list entry. Use *Snooze for 24 hours*.
+
*Expected*: The entry is hidden from the active grocery list. Trigger another scheduled sweep within the 24-hour window.
. After the next sweep, confirm "Whole milk" has *not* been re-added.
. Wait for the snooze window to expire (or use a developer override to advance time). Trigger a sweep.
+
*Expected*: "Whole milk" reappears on the grocery list with the same reason.
. From the active grocery list, *Remove* "Whole milk" outright. Trigger the next sweep.
+
*Expected*: "Whole milk" reappears (Remove is one-shot, not a permanent exclusion), but a single subsequent sweep within the same evaluation window does *not* create a duplicate entry.

*Pass criteria*: Snooze suppresses re-add for the configured window; Remove does not silently re-add within the same sweep; system-added entries are visually distinguishable from user-added ones.

==== MP-MR-03 — Offline Operation and Conflict Surfacing

*Covers*: MR-03 (M3-QA-08), DR-25. *Replaces automated test*: connectivity-simulating integration tests are recommended but not yet present. *Expected duration*: 10 minutes (requires two devices).

. On *device A*, sign in as `test_member`. Place the device in airplane mode.
. While offline, add a new item "Offline cereal" with quantity 1.
+
*Expected*: The item appears in the local inventory list with a pending-sync indicator.
. While device A remains offline, on *device B* (online, signed in as `test_admin`), add an item with the same name "Offline cereal" and quantity 5.
. Take device A out of airplane mode and let it synchronize.
+
*Expected*: The conflict surface (banner, dialog, or merge view) shows both entries and offers a choice: keep both, keep local, keep remote. The local change is *not* silently overwritten.
. Resolve the conflict by keeping both. Verify on device B that both entries are present after the next real-time push.

*Pass criteria*: Pending changes are marked, the conflict is surfaced explicitly, and no data is lost without user acknowledgement.

==== MP-MR-04 — Real-Time Synchronization Across Members

*Covers*: MR-04. *Replaces automated test*: none (requires two real clients connected to a live Supabase project). *Expected duration*: 5 minutes.

. On *device A*, sign in as `test_admin`. On *device B*, sign in as `test_member`.
. On device A, add an item "Sync test". Start a stopwatch when *Save* is tapped.
+
*Expected*: "Sync test" appears on device B without a manual refresh, within the sync target window (≤ 3 seconds under nominal network conditions).
. On device B, edit the quantity of "Sync test" to 5.
+
*Expected*: Device A reflects the new quantity within the same window, also without manual refresh.

*Pass criteria*: Both directions sync without manual refresh and within the documented window.

==== MP-MR-02 — Response Time Walkthrough Timing

*Covers*: MR-02. *Replaces automated test*: not applicable — response time is a usability measurement. *Expected duration*: 10 minutes per participant.

. Recruit one walkthrough participant per persona (Mateo, Sofia, Andrea, Julian — see Section 4.1 Personas).
. Hand the participant a phone with the build under test and ask them to complete the following tasks while standing (simulating a shopping context). Time each task from first tap to confirmation visible:
.. Look up "Whole milk" via the search field.
.. Add a new item "Greek yogurt" with quantity 2 and expiration date one week out.
.. Decrease the quantity of "Whole milk" by 1.
. Record the timing for each task.

*Pass criteria*: No participant abandons a task due to slowness; item creation (task 2) completes in under 60 seconds.
