== Core Inventory Integrity Concerns Relevant to Verification

This subsection keeps only the integrity concerns that directly affect verification of system behavior. The goal is not to restate a full catalog of runtime field-validation rules, but to identify the constraints that must hold for the tested behaviors to remain meaningful.

The following integrity concerns are relevant to verification:

* quantities must not become negative
* item instances must reference valid item types and valid locations
* expiration dates, when present, must remain logically valid
* quantity-changing actions must create a corresponding transaction record
* shared and personal household data must remain distinguishable where required
* household participation changes must not leave invalid access relationships behind

These concerns matter because incorrect stored data would invalidate later behaviors such as low-stock detection, expiration handling, synchronization, transaction history, and shared-household coordination.

Within this section, these concerns are checked through tests and reviews such as:

* checking that quantity updates do not produce invalid inventory states
* checking that expiration handling behaves correctly when dates are present, missing, or unreadable
* checking that quantity-changing actions preserve append-only transaction history
* checking that synchronization does not break household, location, or membership relationships
* checking that shared and personal purchase data remain correctly distinguishable

Detailed field-level constraints and schema-oriented data rules are documented with the corresponding design and data-model material rather than in this validation and verification section.

== Implemented use cases

- Get inventory by owner (numeric id or identifier): `GetInventoryItems` and `GetInventoryItemsByIdentifier` return an `InventoryEntity` assembled from `InventoryModel` and `Product` lookups.
- Add stock to product: `AddInventoryItem` enforces validation (ids > 0, non-empty brand, quantity > 0, non-expired expiration) and appends a `StockModel` to the `stock` JSON for the inventory row.
- Update stock: `UpdateInventoryItem` enforces validation (stock id > 0, non-negative quantity, expiration not in past) and replaces the matching stock entry in the product list.
- Delete stock: `DeleteInventoryItem` removes the matching stock id from the product list and updates the inventory row.

All flows are exposed via `InventoryCubit` which emits `InventoryLoading`, `InventoryLoaded`, and `InventoryError` as appropriate, and refreshes inventory after write operations.

== Validations enforced in code

- Identifier validation: inventory, product, and stock ids must be positive integers (usecases throw `Exception` on invalid ids).
- Quantity validation: add requires `quantity > 0`; update allows `quantity >= 0`.
- Expiration validation: when provided, expiration dates must not be in the past.
- Brand validation: `brand` must not be empty on add/update.

Validation resides in domain usecases (`AddInventoryItem`, `UpdateInventoryItem`, `GetInventoryItems`) and repositories/datasources re-validate inputs as a defense-in-depth measure.

== UI behavior and interactions

- Routes: inventory pages under `/inventory`; product add/edit use `add/:productId` and `edit/:productId/:stockId` path parameters.
- `AddItemPage`: reads `productId` from route, derives `inventoryId` from `AuthCubit` (numeric or identifier), parses expiration input, constructs `StockEntity`, and calls `InventoryCubit.addStock`.
- `EditItemPage`: reads `productId` and `stockId` from route, locates the existing `StockEntity` in `InventoryLoaded` state to pre-fill the form, and calls `InventoryCubit.updateStock` on submit.
- UI surfaces parsing errors (expiration format) and uses `SnackBar` to show success or error messages from cubit state transitions.

== Backend / data-layer behavior

- The `InventorySupabaseDataSource` is the sole Supabase client usage point. It performs:
* `fetchInventoryByOwnerId` / `fetchInventoryByOwnerIdentifier` (SELECT)
* `addStockToInventory` (fetch inventory, append `StockModel`, UPDATE `stock` JSON)
* `updateStockInInventory` (fetch, replace matching id, UPDATE)
* `deleteStockFromInventory` (fetch, remove id, UPDATE)

- Models:
* `InventoryModel.fromJson` tolerantly parses `ownerId` (int or numeric string) and converts stock JSON into `StockModel` objects.
* `StockModel` now includes optional `ownerId` and provides `fromJson`/`toJson` that handle missing ownerId.

== Error handling and state transitions

- Exceptions from Supabase (`PostgrestException`) are wrapped as `DataSourceException`.
- Repositories wrap datasource failures in `RepositoryException` and allow usecases/cubit to surface user-facing messages.
- `InventoryCubit` emits `InventoryLoading` before operations and `InventoryLoaded` or `InventoryError` after; UI reacts to these states.

== Current known limitations

- Per-item visibility: although `ownerId` exists on `StockModel`, the presentation layer does not filter or present per-item ownership; `ownerId` is not used for UI visibility.
- Filtering breadth: UI filtering is limited to category navigation and expiration-focused views. No built-in UI for labels, low-stock thresholds, or range queries.
- Transaction/audit traces: datasource updates the `stock` JSON in-place; it does not create separate transaction/audit rows for quantity changes.
- Concurrency: operations use fetch-modify-update on the `stock` JSON without optimistic locking or version checks; concurrent writes may overwrite intermediate changes.
