== Core Inventory Integrity Concerns Relevant to Verification

This subsection keeps the integrity concerns that directly affect system behavior and documents the current Core Inventory implementation at a behavior level. The goal is not a full catalog of runtime field-validation rules, but to identify the constraints that must hold for the observed flows to remain meaningful and explain how the feature behaves today.

Integrity concerns relevant to verification:

* quantities must not become negative
* item instances must reference valid item types and valid locations
* expiration dates, when present, must remain logically valid
* quantity-changing actions must create a corresponding transaction record
* shared and personal household data must remain distinguishable where required
* household participation changes must not leave invalid access relationships behind

These matter because incorrect stored data would invalidate later behaviors such as low-stock detection, expiration handling, synchronization, transaction history, and shared-household coordination. They are checked through tests and reviews such as: quantity updates do not produce invalid states; expiration handling behaves correctly when dates are present, missing, or unreadable; quantity-changing actions preserve append-only transaction history; synchronization does not break household, location, or membership relationships; and shared and personal purchase data remain distinguishable. Detailed field-level and schema-oriented constraints are documented in the corresponding design and data-model material.

== Core Inventory Verification Summary

This subsection summarizes the current Core Inventory implementation as observed in the repository (not a full field- or schema-level specification, which remains in the design and data-model material). The notes describe behavior at the time of writing on May 24, 2026, focusing on add/edit/remove flows, expiration handling, ownership visibility, and inventory lookup. The "Evidence / notes" column references specific code components and observations from testing and code review.

=== Core Inventory — Implementation Report

[cols="1,2,2",options="header"]
|===
| Area | Current Status | Evidence / notes

| Item creation and editing
| Implemented
| `AddItemPage`, `EditItemPage`, `ItemForm`, `AddInventoryItem`, `UpdateInventoryItem`, and `InventoryCubit` implement add/edit flows. Domain usecases validate inputs; repositories/datasources perform persistence.

| Expiration handling
| Implemented
| Expiration is optional: missing dates are treated as unknown. Domain usecases reject dates earlier than the current moment when provided. Parsing and basic format checking occur in the UI form.

| Remove/delete stock
| Implemented
| `InventoryCubit.deleteStock`, `DeleteInventoryItem`, and `InventorySupabaseDataSource.deleteStockFromInventory` remove stock entries and update the inventory `stock` map in Supabase.

| Ownership / role visibility
| Partially implemented (model only)
| `StockEntity` and `StockModel` include an optional `ownerId` field; JSON parsing/serialization is tolerant. Presentation-layer visibility and filters do not currently act on per-item ownership.

| Inventory lookup and filtering
| Basic filters implemented
| UI exposes category navigation and an expiration-based view. Server-side query support exists for owner-scoped loading; richer lookup/filtering (labels, low-stock thresholds, ranges) is not surfaced in the UI.

| Schema and persistence
| Owner-scoped inventory aggregate
| Inventories are stored per-owner in Supabase with a `stock` JSON map keyed by product id. Datasource operations fetch-modify-update the `stock` JSON and write the full map back to the row.

=== Implemented use cases

- Get inventory by owner (positive integer id or identifier): `GetInventoryItems` and `GetInventoryItemsByIdentifier` return an `InventoryEntity` assembled from `InventoryModel` and `Product` lookups.
- Add stock to product: `AddInventoryItem` enforces validation (ids > 0, non-empty brand, quantity > 0, non-expired expiration) and appends a `StockModel` to the `stock` JSON.
- Update stock: `UpdateInventoryItem` enforces validation (stock id > 0, non-negative quantity, expiration not in past) and replaces the matching stock entry.
- Delete stock: `DeleteInventoryItem` removes the matching stock id and updates the inventory row.

All flows are exposed via `InventoryCubit`, which emits `InventoryLoading`, `InventoryLoaded`, and `InventoryError` and refreshes inventory after write operations.

=== Validations enforced in code

- Identifier validation: inventory, product, and stock ids must be positive integers (usecases throw `Exception` on invalid ids).
- Quantity validation: add requires `quantity > 0`; update allows `quantity >= 0`.
- Expiration validation: when provided, expiration dates must not be earlier than the current moment.
- Brand validation: `brand` must not be empty on add/update.

Validation resides in domain usecases (`AddInventoryItem`, `UpdateInventoryItem`, `GetInventoryItems`); repositories/datasources re-validate as defense-in-depth.

=== UI behavior and interactions

- Routes: inventory pages under `/inventory`; product add/edit use `add/:productId` and `edit/:productId/:stockId` path parameters.
- `AddItemPage`: reads `productId` from route, derives `inventoryId` from `AuthCubit` (numeric or identifier), parses expiration input, constructs `StockEntity`, and calls `InventoryCubit.addStock`.
- `EditItemPage`: reads `productId` and `stockId` from route, locates the existing `StockEntity` in `InventoryLoaded` state to pre-fill the form, and calls `InventoryCubit.updateStock` on submit.
- UI surfaces parsing errors (expiration format) and uses `SnackBar` to show success/error messages from cubit state transitions.

=== Backend / data-layer behavior

- `InventorySupabaseDataSource` is the sole Supabase client usage point, performing:
* `fetchInventoryByOwnerId` / `fetchInventoryByOwnerIdentifier` (SELECT)
* `addStockToInventory` (fetch, append `StockModel`, UPDATE `stock` JSON)
* `updateStockInInventory` (fetch, replace matching id, UPDATE)
* `deleteStockFromInventory` (fetch, remove id, UPDATE)
- Models: `InventoryModel.fromJson` tolerantly parses `ownerId` (int or numeric string) and converts stock JSON into `StockModel` objects; `StockModel` includes optional `ownerId` with `fromJson`/`toJson` that handle a missing ownerId.

=== Error handling and state transitions

- Supabase exceptions (`PostgrestException`) are wrapped as `DataSourceException`; repositories wrap datasource failures as `RepositoryException` so usecases/cubit can surface user-facing messages.
- `InventoryCubit` emits `InventoryLoading` before operations and `InventoryLoaded` or `InventoryError` after; the UI reacts to these states.

=== Current known limitations

- Per-item visibility: although `ownerId` exists on `StockModel`, the presentation layer does not filter or present per-item ownership.
- Filtering breadth: UI filtering is limited to category navigation and expiration-focused views; no UI for labels, low-stock thresholds, or range queries.
- Transaction/audit traces: datasource updates the `stock` JSON in-place without creating separate transaction/audit rows for quantity changes.
- Concurrency: fetch-modify-update on the `stock` JSON has no optimistic locking or version checks, so concurrent writes may overwrite intermediate changes.
