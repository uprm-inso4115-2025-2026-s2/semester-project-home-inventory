== Domain Concept Analysis

This section derives domain concepts from the rough sketch (interviews, observations, edge situations), documenting how specific statements lead to abstractions, identifying term clashes, and defining relationships and invariants that hold independent of any system-to-be.

=== Starting point: raw statements held side-by-side

The following rough-sketch statements anchor concept formation:

* Shared apartment: "If it is not on our fridge note, we assume we are out."
* Shared apartment: "Sometimes I check the pantry before leaving, but by the time I get to Walmart I forgot what we needed."
* Shared apartment: "We have rice in two places. One bag in the kitchen cabinet and another in a plastic bin in the hallway."
* Shared apartment: "Milk is usually bought twice in the same week at least once per month."
* Shared apartment: how they know they are 'low': "when it feels light" or "when we open the backup" (and the backup opening is not recorded).
* Solo student: "If it takes more than a few seconds to log, I won't do it."
* Solo student: buys in bulk; yogurts sometimes expire; estimated 3–5 thrown away last semester.
* Household owner: child sometimes uses last item without saying; toilet paper runs out unexpectedly.
* Household owner: medicines kept separately; expiration dates important; threw away expired medicine without realizing there was a second unopened box.
* Household owner: wants to remove access when someone moves out.
* Student athlete: consumption changes by context ("exam weeks"); buys based on memory of how fast it ran out last time.
* Brainstorming: people describe items as "full", "almost empty", "backup" (rarely with numbers).
* Edge situations: unreadable/missing expiration date; multiple expiration dates within a bulk package; backup stored in car trunk and forgotten.

=== Concept formation: from statements to abstractions

Concepts are derived by asking what phenomena exist, what information households use to act, and what changes over time. Examples:

* "If it is not on our fridge note, we assume we are out." -> *tracked representation* (note/list) vs *reality*, and *assumption under uncertainty*.
* "Rice in two places" -> item storage *location*, and multiple locations for the same item.
* "when it feels light" / "open the backup" -> qualitative, strategy-based *low-stock judgment*, and *backup* as a household practice.
* "Milk bought twice in the same week" -> *duplicate purchase* as a coordination failure from missing shared understanding.
* "3–5 yogurts thrown away" / medicines expired with unopened box -> *expiration* and *batches* (same item type in multiple packages with different expiration dates).
* "remove access when someone moves out" -> *membership* and *access to shared household information*.

=== Core domain concepts (derived)

The Milestone 3 revision adds implementation evidence to each retained concept. Domain terms are preserved for analysis, while implementation aliases identify the classes, repository contracts, schema entities, modules, or documents that carry the concept.

[cols="2,3,4,3",options="header"]
|===
|Concept |Definition (domain-level) |Implementation evidence |Milestone 3 traceability note

|Household
|A living unit (dorm, apartment, shared house) in which one or more people manage household essentials.
|`HouseholdEntity`, `HouseholdModel`, `HouseholdRemoteDataSource`, and `SharingRepository.createHousehold/getHouseholdById`; supporting design in `shared-inventory-definition.adoc` and `software-architecture.adoc`.
|Retained. The Milestone 2 "home/group" wording is standardized as *Household* to match the `sharing_budget` package.

|Household member
|A person who currently belongs to a household and participates in consuming, replenishing, or coordinating around items.
|`HouseholdMemberEntity`, `MemberRole`, `SharingRepository.getMembersByHousehold/addMember/removeMember`, and the `household_members` access-control discussion in `RLSresearch.adoc`.
|Retained. The implementation uses role-bearing membership instead of a generic user-in-group concept.

|Household item
|A physical good kept for everyday use (e.g., milk, rice, toilet paper, soap, medicine).
|Implemented as the aggregate of `ProductEntity` plus one or more `StockEntity` records; persistence mapped by `ProductModel`, `StockModel`, `InventoryModel`, `ProductRepository`, and `InventoryRepository`.
|Retained with clarified scope. In code, "item" is split into product metadata and concrete stock entries.

|Item type
|The kind of item (e.g., "milk") independent of any specific package.
|`ProductEntity` and `ProductModel`; canonical database documentation maps this to `inventory_items` as the logical item definition in `Team2-FinalizedSchema.adoc`.
|Renamed in implementation as *Product*. Treat "item type" and `ProductEntity` as the same abstraction.

|Item instance / package
|A concrete package/unit of an item type (e.g., a specific milk carton, a specific box of medicine).
|`StockEntity` and `StockModel`; `InventoryRepository.addStock/updateStock/deleteStock/getStockForProduct`; canonical schema maps this to `stock_entries`.
|Renamed in implementation as *Stock* or *stock entry*. This matters because expiration and quantity are evaluated per stock entry.

|Inventory
|The collection of household items that exist within a household at a given time.
|`InventoryEntity`, `InventoryModel`, `InventoryRepository`, `InventorySupabaseDataSource`, `InventoryCubit`, and inventory pages/routes under the `core_inventory` feature.
|Retained. Current implementation supports owner-based inventory retrieval; shared-household access is represented by `sharing_budget` entities and architecture docs.

|Tracked inventory record
|A representation of item availability used by household members (fridge note, mental model, list). May diverge from the real inventory.
|`InventoryModel.toJson/fromJson`, `StockModel.toJson/fromJson`, Supabase data sources, and the canonical `inventory_items`/`stock_entries` tables provide the persisted record.
|Retained. The implementation narrows the rough-sketch concept to the app's persisted digital record.

|Availability
|A household's current "how much is left" understanding, often qualitative ("full", "almost empty", "backup").
|`StockEntity.quantity`, `Status` enum (`EMPTY`, `LOW`, `HALFWAY`, `FULL`, `EXPIRED`, `DAMAGED`, `UNKNOWN`), `StockStatus`, and `checkStock()`.
|Retained. Qualitative availability remains in `Status`, while alert automation also computes numeric stock status.

|Quantity (optional formalization)
|A more precise measure of availability (counts/units). The domain can operate without exact numbers.
|`StockEntity.quantity`, `StockModel.quantity`, `AddInventoryItem`, `UpdateInventoryItem`, and `InventoryRepository` stock operations.
|Retained as implemented. Milestone 3 treats quantity as an implemented field, not only an optional analysis idea.

|Low-stock judgment
|A decision that an item is running low, derived from strategies like "feels light", "opened backup", or a numeric threshold.
|`checkStock()`, `StockStatus.lowStock/outOfStock`, `automatedCheckStock()`, `StockCheckResult`, `AutomatedGroceryEngine`, and `low-stock-detection-logic.adoc`.
|Retained with changed abstraction. The domain allows qualitative strategies, but current executable logic uses quantity and a threshold.

|Backup supply
|A household practice of keeping a spare instance/package to reduce the risk of running out.
|Represented indirectly by multiple `StockEntity` records for one `ProductEntity`, by `InventoryEntity.stock` as a product-to-stock map, and by `getStockForProduct()`.
|Retained as partially implemented. There is no dedicated `BackupSupply` class; backups are modeled as extra stock entries.

|Consumption
|Use of items over time (may vary by context such as exams/guests).
|Quantity-changing operations in `InventoryRepository.updateStock/deleteStock`, `UpdateInventoryItem`, and the proposed `stock_changes` table in `Team2-FinalizedSchema.adoc`.
|Retained as partially implemented. Milestone 3 stores current quantity; full consumption-history analytics are schema-supported but not yet a separate domain service.

|Replenishment (restock)
|Acquiring more of an item after consumption reduces availability.
|`InventoryRepository.addStock`, `AddInventoryItem`, `AutomatedGroceryEngine.upsertGroceryListItem`, `GroceryListReason.outOfStock/expired`, and grocery-list screens/use cases.
|Retained. Restock is implemented as adding stock and, for automation, adding grocery-list items when stock or expiration rules require action.

|Expiration date
|A date after which an item instance/package is considered expired or undesirable.
|`StockEntity.expirationDate`, `StockModel.expirationDate`, `checkExpiration()`, `ExpirationStatus`, `automatedCheckExpiration()`, `ExpirationCheckResult`, and `expiration-tracking-logic.adoc`.
|Retained. Expiration moved from item-level language to stock-entry-level implementation.

|Coordination failure
|A situation where members act on inconsistent information (e.g., duplicate purchase, unexpected shortage).
|`DuplicateWarningDialog`, `DuplicateItem`, shared-inventory role flows, invite/member repositories, and `duplicate-handling-rules.adoc` / `document-duplicate-prevention-logic.adoc`.
|Retained as a user-facing risk concept. Evidence exists as prevention/detection UI and supporting rules, not a persistent `CoordinationFailure` entity.
|===

|Deferred

=== Term clashes and clarifications

To prevent inconsistent usage across documentation:

* *Inventory* (real-world items) vs *Tracked inventory record* (note/list/memory); the rough sketch shows these diverge ("not on fridge note -> assume out").
* *Item type* ("milk") vs *Item instance/package* (a specific carton); matters for expiration and "second unopened box".
* *Low-stock* is not inherently numeric; in the domain it is often qualitative ("feels light", "open backup").
* *Backup* is a domain concept (household practice), not an application feature.
* *Household membership* changes over time ("remove access when someone moves out"): membership is a domain phenomenon; access control is a derived system concern.

=== Relationships (domain model)

Relationship rows inherit implementation status from the concept tables above. Rows involving deferred concepts are domain-analysis evidence, not completed implementation claims.

[cols="2,2,4",options="header"]
|===
|Concept A |Concept B |Relationship

|Household (`HouseholdEntity`) |Household member (`HouseholdMemberEntity`)
|A household has one or more members; membership may change over time.

|Household (`HouseholdEntity`) |Inventory (`InventoryEntity`)
|A household has an inventory (items that exist in the household).

|Household item |Item type (`ProductEntity`)
|Each household item corresponds to an item type.

|Item type (`ProductEntity`) |Item instance/package (`StockEntity`)
|An item type may have multiple instances/packages at once (bulk buying, backup supply).

|Item instance/package (`StockEntity`) |Location (deferred)
|Deferred relationship. The domain allows item instances stored in locations, but Milestone 3 code does not persist location on `StockEntity`.

|Item instance/package (`StockEntity`) |Expiration date (`StockEntity.expirationDate`)
|Some item instances have an expiration date; others do not.

|Household member (`HouseholdMemberEntity`) |Consumption / replenishment (`InventoryRepository.updateStock/addStock`)
|Members consume and replenish items; consumption rates vary by context (exam weeks, guests).

|Tracked inventory record (`InventoryModel`/`StockModel`) |Inventory (reality)
|Tracked records approximate reality and may be incomplete, outdated, or wrong.

|Household (`HouseholdEntity`) |Coordination failure (`DuplicateWarningDialog` / invite flows)
|Coordination failures arise when members act on inconsistent or outdated tracked records.
|===

=== Events, actions, and behaviors (domain-level)

* Events (instantaneous state changes): an item becomes *out* (unexpected shortage); becomes *low* (e.g., "backup opened"); expires or is discovered expired.
* Actions (intentional acts): check availability (pantry/fridge-note check); consume an item; replenish an item.
* Behaviors (ongoing processes): household maintenance cycle (consume -> notice low/out -> decide purchase -> replenish -> store -> repeat); shared-household coordination (negotiate who buys what, or fail and duplicate-buy).

=== Invariants (domain rules)

* I1: A household has at least one member while it is active.
* I2: In the real-world domain, an item instance/package is stored somewhere, but explicit location tracking is deferred until a stable location field or room entity exists.
* I3: Not all judgments require numeric quantities; qualitative availability ("full", "almost empty", "backup") is valid domain information.
* I4: If an item instance has an expiration date, it can become expired without being consumed, creating waste.
* I5: A household may possess multiple instances of the same item type simultaneously (bulk buying, backups).
* I6: Tracked records can diverge from reality; decisions may be made under uncertainty ("not on note -> assume out").

=== Edge cases and risks (from rough sketch)

* E1: Same item type in multiple locations (rice in cabinet + hallway bin) -> risk of undercounting or duplicate purchase; tracking deferred with the Location concept.
* E2: Backup supply opened but not recorded -> low-stock event not propagated to shared understanding.
* E3: Consumption rate varies by context (exam weeks, guests) -> replenishment based on "last time" memory becomes unreliable.
* E4: Multiple expiration dates in a bulk package -> motivates future batch-level tracking.
* E5: Expiration date unreadable/missing -> household cannot reliably judge expiration status.
* E6: Membership change (move-out) -> household must update who participates and who is informed.

=== Ownership structures for shared inventory items

The rough sketch shows household items behave differently in shared environments — some are clearly shared essentials, others managed personally — so ownership must be analyzed as a domain concept rather than assumed to have one structure. Structures are evaluated on their ability to support collaborative interaction, preserve clear responsibility attribution, align with domain invariants, support enforceable permission logic, and represent domain relationships coherently without unnecessary complexity.

==== User-owned structure

An item belongs primarily to an individual; shared use is added on top of individual ownership.

----
Item -> User
Item associated with Household context
----

This provides strong individual accountability and ownership-based authority but does not fit shared-household semantics naturally, since the item is conceptually owned by a person first. Most suitable when items are primarily personal contributions that only occasionally appear in a shared environment.

==== Group-owned structure

An item belongs to the shared household context rather than a specific person; members interact through membership.

----
Household -> Item
Household member -> Membership -> Household
----

This supports shared use naturally and aligns with communal resources, but provides no inherent responsibility attribution — if the domain needs to represent who is responsible for a shared item, that must be added separately. Most suitable when items are treated as collective household resources.

==== Hybrid structure

An item exists within the shared household context but may also be associated with a responsible member when needed.

----
Household -> Item
Household member -> Membership -> Household
Membership or responsibility relation -> Item
----

This preserves the shared context while allowing responsibility attribution, supporting both collaboration and accountability, though it is conceptually more complex. Most suitable when the domain must represent both shared items and items with a clearer responsible participant.

==== Recommendation

The hybrid structure provides the strongest overall conceptual fit: it preserves the shared household context, supports collaboration naturally, allows responsibility attribution when needed, aligns with membership-based participation, and provides a flexible basis for later permission and ownership rules. It does not require every item to behave the same way; instead it represents both shared and personal responsibility within one coherent household model.

Implementation evidence is split across current code and supporting design artifacts: shared context is represented by `HouseholdEntity`, `HouseholdMemberEntity`, `MemberRole`, and `SharingRepository`; item-level responsibility by `StockEntity.ownerId` and owner fields in inventory/sharing models; role-based sharing behavior is documented in `shared-inventory-definition.adoc`, `permission-rules-definition.adoc`, and `RLSresearch.adoc`. The *user-owned* and *group-owned* structures are therefore analysis alternatives, while the hybrid model is the Milestone 3 implementation direction.
