=== Risk Identification using FMEA and Guidewords

This section identifies requirement-level risks using two structured techniques — Failure Mode and Effects Analysis (FMEA) and Guideword analysis — to surface realistic failure situations and edge cases affecting the system's reliability, usability, correctness, and trust.

==== FMEA Risk Case 1 — Incorrect Quantity After Transaction

[cols="1,4",options="header"]
|===
|Field |Description

|Failure mode
|The quantity in a tracked inventory record becomes incorrect after a transaction is recorded.

|Cause
|A transaction is recorded with the wrong quantity, multiple members update the same record close together, or a manual adjustment is entered incorrectly.

|Effect on the system
|Low-stock judgment may become incorrect, alert/notification records may be triggered unnecessarily or not when needed, and the restock list/planner may contain incorrect item types.

|Severity
|8

|Occurrence
|5

|Detection
|5

|Risk Priority Number
|200

|Scenario
|One member records replenishment while another records consumption for the same record. The final recorded quantity does not reflect actual inventory, causing an incorrect low-stock judgment.
|===

==== FMEA Risk Case 2 — Scheduled Sweep Does Not Run

[cols="1,4",options="header"]
|===
|Field |Description

|Failure mode
|The scheduled sweep does not execute at the expected time.

|Cause
|Scheduler failure, missed cron execution, service downtime, or configuration errors in the automation process.

|Effect on the system
|Near-expiry and expired item instances are not evaluated on time, low-stock conditions may remain undetected, and alert/notification records may be delayed or not created.

|Severity
|9

|Occurrence
|3

|Detection
|4

|Risk Priority Number
|108

|Scenario
|The sweep is expected to run once per day, but an automation failure prevents the run. Expired item instances remain undetected until a later run or manual review.
|===

==== FMEA Risk Case 3 — Duplicate Alert / Notification Records

[cols="1,4",options="header"]
|===
|Field |Description

|Failure mode
|The system creates duplicate alert/notification records for the same unchanged condition.

|Cause
|State transitions are not checked correctly, deduplication rules are incomplete, or retries reinsert the same record.

|Effect on the system
|Members may experience notification fatigue, ignore future alerts, or lose trust in the automation.

|Severity
|7

|Occurrence
|4

|Detection
|4

|Risk Priority Number
|112

|Scenario
|A record remains LOW_STOCK across several evaluations. If the system creates a new alert each time without checking whether the state changed, duplicate records accumulate.
|===

==== Guideword Case 1 — Missing

A member consumes or replenishes an item type but does not record the transaction, so the tracked record diverges from reality, low-stock judgment becomes less reliable, and later automation decisions may be incorrect. *Mitigation:* support low-friction logging, allow quick manual adjustments, and use transaction history to correct records over time.

==== Guideword Case 2 — Delayed

The scheduled sweep runs later than expected, so near-expiry or expired item instances are detected after the intended time; alerts are generated late, members may not act in time, and expired items may remain in use longer. *Mitigation:* record the last successful sweep run, detect missed runs, and execute a catch-up sweep when necessary.

==== Guideword Case 3 — Duplicate

The same item type is repeatedly added to the restock list/planner even though it is already present, cluttering the list, confusing members, and making the system appear unreliable. *Mitigation:* require deduplication before auto-add, allow manual removal, and re-add only when a new qualifying state transition occurs.

==== Relationship to Requirement Concepts

These risks relate directly to requirement-level concepts identified earlier: *Fast capture* (missing transactions), *Tracked record vs reality* (quantity drift), *Scheduled sweep* (delayed/missing runs), *State transition* (duplicate alerts), and *Auto-add to restock list/planner* (duplicate entries and user-control concerns). This analysis supports later design decisions, validation activities, and reliability considerations.
