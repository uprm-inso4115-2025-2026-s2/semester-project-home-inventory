== Purpose

Systematically identify, categorize, and resolve inconsistencies within the current system requirements — terminology inconsistencies, timing conflicts, overlapping features, and contradictions between functional and non-functional requirements. === Problem

Different documents use different terms for similar concepts: "item" vs item type/item instance; "stock change" vs transaction (quantity change); "inventory item"; "stock item"; "product" vs item type; "grocery item" vs item type; "grocery list" vs restock list/planner; "user" vs household member; "notification record/event" vs alert/notification record. This creates ambiguity about whether these are different entities or the same entity in different contexts.

=== Resolution

Revise the official terminology list in `terminology.adoc` and align all documents to it (for example, change all "user" to "household member" in Section 3.1 documents).

=== Final Decision

All documents in Section 3.1 must use the standardized terminology defined in `terminology.adoc`. Synonyms such as "inventory item", "stock change", "product", "grocery item", and "user" are replaced with the official terms:
- tracked inventory record
- transaction
- item type
- item instance
- household member
- restock list / planner (used interchangeably depending on context)
- alert / notification record (used interchangeably depending on context)

Terminology definitions exist only in `terminology.adoc`; other documents use the terms without redefining them.

== Timing Conflicts

=== Documents Containing Issues
- automation-check-system.adoc
- definition-expiration-alert-system.adoc
- evaluationOfNotification.adoc
- low-stock-research-strategies.adoc

=== Problem

Some documents describe real-time detection, scheduled daily sweeps, cron jobs, and polling mechanisms, creating ambiguity about when alerts should be generated and when automation logic should run.

=== Resolution

Apply the already-defined rules consistently across documents and clarify when sweeps happen and when alerts are generated (e.g., in `definition-expiration-alert-system.adoc`, expiration and near-expiry conditions are evaluated during the scheduled sweep, and alerts are only generated on a state transition).

=== Final Decision

The system follows a hybrid timing model:

- Immediate evaluation after each transaction detects low-stock and out-of-stock state transitions.
- A scheduled sweep runs once per day to evaluate expiration, near-expiry, and low-stock conditions for items that have not recently changed.
- Alert / notification records are generated only when a state transition is detected, not continuously while a condition remains true.

This model must be reflected consistently across all automation, expiration, and notification documents.

== Overlapping Feature Responsibilities

=== Documents Containing Issues
- low-stock-research-strategies.adoc
- grocerylist_autoadd_decisionlogic.adoc
- automation-check-system.adoc
- definition-expiration-alert-system.adoc

=== Problem

Low-stock detection, expiration alerts, grocery auto-add, and notifications overlap in responsibilities, so it is unclear which subsystem triggers each action (e.g., low stock triggers both alerts and restock auto-add; expired items trigger both notifications and auto-add). This creates unclear system boundaries.

=== Resolution

In each feature document, clearly define the responsibility boundary (e.g., expiration-related state detection belongs to the Automation System, while creation of alert/notification records belongs to the Notification Service).

=== Final Decision

System responsibilities are separated as follows:

- Transactions only record quantity changes and update tracked inventory records.
- The Automation System evaluates low-stock, near-expiry, expired, and out-of-stock conditions and detects state transitions.
- The Notification Service creates alert / notification records.
- The Restock List / Planner system adds item types to the restock list when specific state transitions occur.

Each subsystem performs only its defined responsibility to avoid overlap.

== Data Model vs Transaction Model Conflict

=== Documents Containing Issues
- schema-for-inventory-&-stock-changes.adoc
- inventory-transaction-tracking.adoc

=== Problem

The system includes tracked inventory records that store current quantity and transaction (quantity change) records that track history. It is unclear whether current quantity is stored directly or derived by replaying all transactions, creating ambiguity in the data model.

=== Resolution

Tracked inventory records store the current quantity and are updated whenever a transaction is recorded. Transaction records are append-only historical records explaining how the current quantity was reached, not the primary source for computing current quantity during normal operation.

=== Final Decision

Tracked inventory records store the current quantity directly; transactions are append-only historical records explaining how it was reached. When a transaction is recorded, the tracked inventory record quantity is updated immediately. Current quantity is not computed by replaying all transactions during normal operation — transactions are used for history, auditing, and analytics.

== Notification System Responsibility Conflict

=== Documents Containing Issues
- notifications_supabase_schema.adoc
- automation-check-system.adoc
- evaluationOfNotification.adoc
- definition-expiration-alert-system.adoc

=== Problem

It is unclear which subsystem creates alert/notification records after conditions are detected; different documents assign this to the Automation System, database triggers, the expiration/low-stock logic, or a Notification Service, creating unclear responsibility boundaries.

=== Resolution

Clarify that the Automation System evaluates conditions and detects state transitions, then triggers downstream notification handling (without owning delivery). The Notification Service creates alert/notification records, the application displays in-app records, and push delivery (if enabled later) belongs to the Push Service.

=== Final Decision

The Automation System detects state transitions (LOW_STOCK, OUT_OF_STOCK, NEAR_EXPIRY, EXPIRED) and, on a relevant transition, triggers the Notification Service. The Notification Service creates alert / notification records; the application interface displays in-app notifications; and push delivery, if implemented later, is handled by a separate Push Service. This separation ensures clear boundaries and prevents overlap.

=== Requirement Concept Overlap

Concept overlaps were fixed while addressing the other categories — for example, "state transition" was clarified for both low-stock and expiration detection, resolving overlaps between those features and their alerts and notifications.

== Conclusion

Based on the identified problems, the system architecture should follow this flow:

Tracked Inventory Records → Transactions (Quantity Changes) → State Evaluation → Automation → Alert / Notification Records + Restock List / Planner Auto-Add

Defining subsystem responsibilities and terminology resolves most requirement clashes.
