== Traceability

This section describes how traceability is established in the project. Traceability means our deliverables are linked so we can answer where requirements come from, which personas they serve, and how they connect to domain concepts, scenarios, and verification artifacts. When something changes, we can see what else might be affected — for example, modifying a requirement reveals which personas and needs it supports, which user stories are impacted, and which scenarios/tests should be revisited. The approach keeps links clear without overcomplicating the documentation.

=== Traceability approach (labels and links)

We maintain traceability through a simple labeling system.

==== Persona goals

Each persona's goals are labeled with a short code.

* **Mateo (M)**: **MG1** know what I have without extra effort; **MG2** avoid wasting expired food; **MG3** avoid running out of daily essentials.
* **Sofia (S)**: **SG1** stay within a strict budget; **SG2** split shared costs fairly; **SG3** avoid duplicate purchases.
* **Julian (J)**: **JG1** avoid running out of specialty items; **JG2** avoid waste from bulk purchases; **JG3** keep personal items separate.
* **Andrea (A)**: **AG1** coordinate shared stocking without mental overload; **AG2** get reimbursed accurately; **AG3** know what is needed before bulk shopping.

==== Needs ↔ requirements

Each requirement in Section 2.2 is tagged with which Needs IDs (N1–N5) it supports, and when helpful which persona goals.

.Example
* **IR-01 (Item Initialization)** → Needs: N1, N2 | Goals: MG1, JG1, AG3
* **IR-04 (Low-stock thresholds)** → Needs: N2 | Goals: MG3, JG1, AG1
* **IR-07 (Cost splitting)** → Needs: N5 | Goals: SG2, AG2

==== User stories ↔ requirements

Each user story in Section 2.2.1 lists which interface requirements it implements.

.Example
* **US-INV-01** → Implements: IR-01, IR-02, IR-03, IR-05
* **US-ALT-01** → Implements: IR-04
* **US-SB-01** → Implements: IR-06, IR-07
* **US-RPT-01** → Implements: IR-08

==== Domain concepts ↔ requirements

Domain concepts from Section 2.1 are linked to the requirements that depend on them.

.Example
* **Item type / Item instance** → IR-01, IR-02, IR-05
* **Household / Household member** → IR-03, IR-06, IR-07
* **Low-stock threshold** → IR-04
* **Expiration date** → IR-05
* **Spending entry / Budget (optional scope)** → IR-06, IR-07, IR-08

==== Scenarios/tests ↔ requirements (Milestone 1)

Traceability extends to the main V&V artifacts: scenario IDs **S1..Sx** (Section 3.2.1), test case IDs **TC-*** (Section 3.2.3), and walkthrough findings **WF-*** (Section 3.2.2) once real sessions are performed.

.Example
* **S1 (Low-stock after consumption)** → IR-02, IR-04 → TC-ALT-01, TC-AUTO-01
* **S2 (Avoid duplicate purchase in shared household)** → IR-03, IR-08 → TC-INV-05, TC-RPT-01

=== Questions traceability helps answer

* Which personas and needs are affected if a requirement changes?
* Which scenarios/tests must be revisited to verify the changed requirement?
* Which domain concepts are involved in a given requirement (to avoid terminology drift)?
