== Inconsistency Management

An exploration of our domain terminology, database schema, events, actions and behaviors, shared inventory definition, and duplicate item criteria revealed two inconsistencies.

* **Event naming clash — "An Inventory has been generated":** This event, triggered by adding an item to the inventory for the first time, was described as changing the inventory to reflect a new item. But _Inventory_ is defined as "the list of available products in a home," while _Item_ (a synonym for _Stock_) is "an instance of a product." The name implied creating an inventory, but the described change modified an already-existing inventory. Resolution — the event was split into two:
** "An Inventory has been generated" was updated so its "What changed" reads: "The inventory is created and reflects the presence of the new item," separating inventory creation from modification and clarifying that the inventory is created as a direct result of adding the first item.
** A new event, **"A new Product has been generated,"** was introduced for when an item is added with no relation to an existing product; it records the inventory change reflecting the new product description plus the item count and description.

* **Ownership multiplicity mismatch — Group-Owned Inventory model:** The Shared Inventory Definition's Group-Owned model maps all items as belonging to the household, with multiple members able to add, edit, and delete them, and describes inventories with multiple stock entries that may carry linked owner tags — implying items can have multiple owners. However, the ER and table diagrams only allowed exactly one owner per item. Resolution — the ER and table diagrams were updated so the item–owner relationship is many-to-many with total participation on both sides, adding a new **Owns** table. This lets an item be owned by multiple members while preserving a member's ability to own multiple items.
