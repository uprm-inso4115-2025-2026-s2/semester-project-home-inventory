== Invites Logic Definition

=== Core Concepts

#The terms *Invitation*, *Owner*, *Member*, *Household*, *Membership*, and *Permission rule* are defined in <<_terminology>>. The attribute schema for an *Invitation* (sender, recipient, target household, status, expiration timestamp) is documented in the entities section. This document does not redefine those terms; it specifies invitation-permission policy, lifecycle behavior, and validation rules built on them.#

==== Invitation Permissions

Permissions determine what user is allowed to send invitations.

Users with the appropriate permissions can include:

* Owner-Only
** Only the household Owner may send invitations.

* Role-Based
** Owners and designated Members may send invitations.

By default, invite permissions can only be made by Owners, unless Member permissions are expanded.

=== #Invitation Lifecycle Behavior#

#The canonical invitation lifecycle states — *pending*, *accepted*, *declined*, *expired*, *revoked* — are defined under *Invitation* in <<_terminology>>. The subsections below describe only the operational behavior of the system in each state.#

==== #pending#
- #Invitation has been created and delivered; awaiting recipient response.#
- #Editable or revocable by the sender.#

==== #accepted#
- #Recipient has joined the household; the invitation becomes inactive.#
- #Permissions are assigned based on the role configured at acceptance.#

==== #declined#
- #Invitation becomes inactive.#
- #Sender may issue a new invitation.#

==== #expired#
- #Cannot be accepted; the invitation is automatically marked inactive.#
- #A new invitation must be sent to re-invite the recipient.#

==== #revoked#
- #Sender or Owner cancels the invitation before acceptance.#
- #The recipient can no longer join using that invitation; it becomes inactive.#

=== Validation Rules

==== Duplicate Invites
- Only allow invitations made to the same user for the same household to be editable, not duplicated.
- Allow resend only after expiration, decline, or revocation.

==== Expiration Timing
- Default expiration window: 72 hours (editable by inviter).
- System should automatically invalidate expired invites.
- Expired invites are not reusable.

=== Expected System Behaviors

==== Invite Acceptance
- User gains access immediately upon confirmation.
- Assigned default Member role unless specified otherwise.
- Notification sent to existing household members.

==== Invite Rejection
- Invitation marked Declined.
- No access granted.
- Sender notified of rejection.
- Household is notified of the declined invitation.

==== Invite Cancellation
- Sender or Owner may revoke before acceptance.
- Invitation becomes invalid instantly.
- Houselhold Members are notified of the cancellation.
- Recipient invite becomes unusable.

==== User Joining via Link vs Direct Invite

* Direct Invite
** Recipient receives invite through application.
** Invited user must have an account or create one to accept.

* Link Invite
** Shareable link allows multiple recipients.
** Requires validation step before access is granted.
** Will require user to create an account or log in before joining.

=== Security Considerations

- Invitations must use secure tokens.
- Tokens should be single-use or time-bound.
- Server-side validation required for all joins.

=== Success Criteria

* Invitation lifecycle states clearly defined.
* Permission rules documented.
* Validation rules prevent misuse or duplication.
* Acceptance and rejection flows explicitly described.
* Understandable to both technical and non-technical team members.
* Ready to guide implementation of onboarding and access control.
