== Interface Requirements

Interface requirements describe how domain phenomena and concepts are represented within the system, how users interact with those representations, and how important system state changes become visible through the user interface. These requirements were derived through elicitation activities including semi-structured interviews, lightweight story mapping, and scenario walkthroughs focused on realistic shared-household inventory behavior.

[NOTE]
====
The IRs below are mapped against concrete user-story executions in <<_requirements_walkthroughs>>. Two systematic findings affect this set in particular: (1) several IRs use *display-only* verbs ("indicate reimbursement status" in IR-07, "provide a means to mark" in IR-03) where the user story actually needs read/write — see findings REQ-FUZZY-R4c, REQ-GAP-R3b; and (2) IR-15's snooze coverage names *restock entries* but not *alerts*, even though DR-14 references an alert snooze period — see REQ-FUZZY-R2b. The consolidated findings table at the end of that walkthrough lists every fix recommended against this IR set.
====

* IR-01: Item Initialization



When a household member acquires a new item, they need a way to create a corresponding representation in the system.
+
*The system shall provide a means for household members to add new inventory items, including item name, quantity or availability, category, storage location, ownership status (personal or shared), and optional expiration date information.*

Needs: N1, N2 | Goals: MG1, JG1, AG3 | Domain concepts: Item type, Item instance, Location

* IR-02: Item Update on Consumption


When a household member consumes part of an item, they need a way to update the tracked representation to reflect the remaining availability.
+
*The system shall provide a means for household members to record consumption by decreasing recorded quantity or availability values, or by marking an item as finished or out-of-stock.*
+
Needs: N1, N2 | Goals: MG1, MG3, JG1 | Domain concepts: Item instance, Quantity, Consumption

* IR-03: Ownership Specification



When inventory is shared among multiple household members, users need visibility into whether items are personal or shared.
+
*The system shall provide a means to mark inventory items as personal or shared and, when applicable, associate personal items with a specific household member.*
+
Needs: N4 | Goals: SG3, JG3 | Domain concepts: Household member, Item instance, Membership

* IR-04: Low-Stock Threshold Definition



When household members manage inventory levels, they need interface controls for defining low-stock thresholds for individual items.
+
*The system shall provide controls for entering and editing low-stock threshold values during item creation and item-editing workflows. The interface may also provide quick-edit controls when an item is currently flagged as low-stock.*
+
Needs: N2 | Goals: MG3, JG1, AG1 | Domain concepts: Low-stock threshold, Item type

* IR-05: Expiration Date Entry



When household members manage perishable items, they need a way to record and edit expiration-date information.
+
*The system shall provide a means to enter and edit expiration dates for inventory items that expire while also supporting items without expiration-date information.*
+
Needs: N2 | Goals: MG2, JG2 | Domain concepts: Item instance, Expiration date

* IR-06: Purchase Logging



When household members spend money on household items, they need a way to record those purchases in the system.
+
*The system shall provide a means to log purchases, including purchased items or categories, total cost, purchase date, and whether the purchase was personal or shared.*
+
Needs: N5 | Goals: SG1, AG2 | Domain concepts: Spending entry, Spending category

* IR-07: Cost Splitting



When household members record shared purchases, they need an interface for viewing participant selections and reimbursement information.
+
*The system shall provide a means to record shared purchases, display participant selections, show split summaries, indicate reimbursement status, and allow users to review or update shared purchase information through the interface.*
+
Needs: N5 | Goals: SG2, AG2 | Domain concepts: Spending entry, Household member, Membership

* IR-08: Dashboard Metric Overview



When household members review household inventory status, they need a high-level overview without navigating through multiple detailed views.
+
*The system shall provide a dashboard view summarizing key inventory and household metrics such as total tracked items, low-stock items, expiring or expired items, and current-period spending information.*
+
Needs: N1, N3 | Goals: MG1, AG1, AG3 | Domain concepts: Inventory, Budget status, Low-stock threshold, Expiration date

=== Appendix A: Edge-Case Interface Requirements

The following edge-case interface requirements are recognized but deferred for detailed specification in later milestones. They are captured separately from the core interface requirements to preserve scope awareness and future traceability.

==== IR-EC-A: Near-Duplicate Variant Disambiguation

When a user adds an item whose name matches an existing item type but whose size, variant, or brand differs, the system shall highlight the conflicting attribute and require the user to choose between creating a different variant or using the existing item type. Same-name items with different variants shall not be automatically merged by default.

==== IR-EC-B: Stock Entry Separation by Expiration and Location

When a user attempts to merge item instances that have different expiration dates or storage locations, the system shall warn that merging may remove expiration or location tracking information. The default action shall preserve separate entries unless explicit confirmation is provided.

==== IR-EC-C: Import Idempotency and Duplicate Spend Prevention

When a user uploads a CSV import file that was previously imported, the system shall default to a review workflow and display a summary of potential duplicate transactions. Matching transactions shall require explicit confirmation before duplicate import actions occur.

==== IR-EC-D: Inventory Correction Without Budget Impact

When a user deletes or merges inventory entries associated with spending records, the system shall present separate controls for inventory correction and budget correction. Inventory adjustments shall not automatically remove spending-history records.

==== IR-EC-E: Refund and Return Flow

When a user returns a purchased item, the system shall provide a refund workflow supporting inventory adjustment, refund amount entry, refund date entry, and optional linkage to the original receipt or spending record.

==== IR-EC-F: Waste and Shrinkage Adjustment

When a user removes expired, lost, or consumed inventory outside standard purchase or return workflows, the system shall provide adjustment controls requiring an adjustment reason and optionally allowing the adjustment to appear in waste reporting views.

==== IR-EC-G: Shared Household Budget Attribution Prompt

When a user adds inventory items within a shared household, the system shall prompt for purchaser attribution and require confirmation before assigning purchases to another household member.

==== IR-EC-H: Undo for Auto-Merge Actions

When inventory quantities are automatically merged, the system shall provide an undo control allowing users to reverse the merge operation within a limited time window.

==== IR-EC-I: Audit Trail for Edge-Case Resolutions

When edge-case resolutions modify inventory state, the system shall generate an audit log entry containing relevant inventory, user, household, and action metadata accessible to authorized household administrators.

=== Milestone 3 Additional Interface Requirements

* IR-09: Role-Based Visibility and Permission Controls
When household members interact with shared inventory, they need interface behavior that reflects ownership visibility and household permissions.

*The system shall provide interface behavior reflecting household role and ownership rules. Personal items shall be hidden from non-owners by default, while shared items and administrative controls shall be visually separated according to household permissions.*
+
Needs: N4, N5 | Goals: SG3, JG3, AG2 | Domain concepts: Household member, Membership, Ownership, Item instance
+
M3 source: M3-QA-01, M3-QA-02.


* IR-10: Filtered Inventory Lookup
When household members search for inventory information, they need filtering and lookup controls supporting rapid inventory access.

*The system shall provide inventory lookup controls for item name, category, location, ownership scope, stock status, and expiration status.*
+
Needs: N1, N3, N4 | Goals: MG1, SG3, AG3 | Domain concepts: Item type, Location, Availability, Ownership
+
M3 source: M3-QA-03.


* IR-11: Fast Manual Entry After Barcode Failure
When barcode scanning fails or is unavailable, household members need a fast fallback workflow for manual inventory entry.
+
*The system shall provide a manual-entry fallback allowing users to save inventory items with only item name and quantity or availability required. Optional information may be entered immediately or deferred until later editing.*
+
Needs: N1, N2 | Goals: MG1, JG1, AG3 | Domain concepts: Item type, Item instance, Quantity, Availability
+
M3 source: M3-QA-04.


* IR-12: Barcode Scanning and Manual Entry Fallback
When household members add inventory items using barcode scanning, they need a reliable fallback workflow if scanning fails or no matching product is found.
+
*The system shall provide barcode-scanning functionality using the device camera for item identification. If barcode scanning fails, is unavailable, or produces no matching product result, the interface shall immediately transition to a manual-entry workflow requiring only item name and quantity or availability to create a minimum viable inventory record. Optional information may be entered immediately or deferred until later editing.*
+
Needs: N1, N2 | Goals: MG1, JG1, AG3 | Domain concepts: Item type, Item instance, Barcode, Quantity, Availability
+
M3 source: M3-QA-04.


* IR-13: Budget Alert Preferences
When household members manage spending goals, they need interface controls for reviewing and adjusting budget-related notifications.
+
*The system shall provide controls for enabling or disabling budget threshold alerts. Household members shall be able to review warning thresholds and adjust notification preferences through the interface.*
+
Needs: N5 | Goals: SG1, AG2 | Domain concepts: Budget, Budget cycle, Budget threshold crossing, Spending entry
+
M3 source: M3-QA-05.


* IR-14: Shared Alert Audience and Delivery Preferences
When household members receive shared alerts, they need visibility into those alerts and control over how notifications are presented.
+
*The system shall provide a means for authorized household members to view shared household alerts and configure delivery preferences such as push notifications or grouped summaries. The interface shall support reviewing and dismissing visible alerts.*
+
Needs: N2, N4, N5 | Goals: MG2, AG1, SG3 | Domain concepts: Alert / notification record, Household, Household member, Actionable state
+
M3 source: M3-QA-06.


* IR-15: Restock List Override Controls
When automatically generated restock recommendations appear, household members need interface controls for managing those entries.
+
*The system shall provide controls allowing authorized household members to remove, dismiss, or snooze restock list entries. The interface shall indicate whether a restock entry was manually created or automatically generated.*
+
Needs: N2, N5 | Goals: AG1, AG3, SG3 | Domain concepts: Restock list / planner, Replenishment, Low-stock judgment, Alert dismissed / deferred
+
M3 source: M3-QA-07.
