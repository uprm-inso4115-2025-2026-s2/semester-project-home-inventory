=== Feature 1: Core Inventory Management (F-INV)

**Primary Users:** Household managers, kitchen coordinators

==== Item Lifecycle State Diagram

The following state diagram documents how a tracked inventory item changes state after it enters the system. It connects the implemented Core Inventory flow (`F-INV`) with automated stock and expiration evaluation (`F-AUTOCHECK`), alert generation (`F-ALERT`), grocery-list restocking (`F-GL-AUTO` / `F-GL-USER`), and the documented historical-preservation rule for archived items (`DR-3`). The diagram is intentionally focused on item lifecycle state rather than notification lifecycle state.

image::diagrams/item_lifecycle_state_diagram.png[Tracked Inventory Item Lifecycle State Diagram, width=100%]

Source file: `docs/2-descriptive/implementation/diagrams/item_lifecycle_state_diagram.mmd`

The diagram shows the tracked inventory item lifecycle from acquisition through active use, alert-worthy states, exception states, disposal, and archival.

**Transition interpretation:**

* `Acquired` begins when a household member adds an item through barcode scanning or manual entry.
* `InStock`, `LowStock`, and `OutOfStock` are availability states derived from quantity and low-stock threshold rules. Quantity changes are expected to trigger state re-evaluation.
* `NearExpiry` and `Expired` are expiration states derived from the item's expiration date during scheduled checks.
* `Discarded` represents a user decision that the physical item is no longer kept or usable.
* `Archived` is a non-active record state used to keep historical references while excluding the item from active inventory views.
* `Lent` and `Lost` are marked as conceptual because current documentation recognizes outside-household and lost-item scenarios, but the current implementation evidence does not show them as fully implemented Core Inventory states.

**Implementation alignment:**

The implemented Core Inventory feature supports adding, editing, viewing, and quantity/expiration updates for item records. The automated check logic evaluates low-stock, out-of-stock, near-expiry, and expired conditions, while grocery-list automation can replenish or restock an item after shopping. Archival is modeled as the preferred preservation behavior when an item should no longer appear in active inventory views, especially when financial or alert history may still reference the item. Conceptual states must not be presented as completed functionality until their UI, data model, and operation behavior are implemented and verified.

=== Feature 2: Automated Expiration Alerts & Notifications (F-ALERT + F-AUTOCHECK)

**User Value:** Prevents food waste by proactively alerting users before items spoil. Removes the mental burden of manual fridge checks, especially critical for busy users like Mateo.

**Primary Users:** All household members (push notifications), household admin (alert configuration)

**End-to-End User Flow:**

.Alert Generation & Delivery Pipeline
[cols="2,3,2", options="header"]
|===
| **Input**
| **Processing**
| **Output**

| Supabase Cron job triggers daily at 08:00 UTC
| 1. Query all non-archived items in `products` table
2. Calculate days until expiration for each item
3. Apply alert thresholds (e.g., notify if expires in ≤ 3 days)
4. Deduplicate: skip items already notified in last 24h (check `alert_log`)
5. Build payload with expiring items
| List of items meeting alert criteria, ready for notification

| Alert payload generated (item name, expiration date, action URL)
| 1. Validate user FCM/APNs token availability
2. Format payload with deep link to Alerts Center
3. Send via Firebase Cloud Messaging (FCM) or Apple Push Notification service (APNs)
| Push notification delivered to user's device

| User taps push notification on mobile device
| App route handles deep link and navigates to the "Alerts Center" tab to highlight expiring items
| Alerts Center screen displays:
- List of expiring items sorted by urgency
- Recommended actions (consume, donate, discard, extend date)
- Quick action buttons

| User taps "Mark as Consumed" or "Extend Expiration" for an item
| 1. If Mark Consumed: delete or reduce quantity to 0
2. If Extend: show date picker, update expiration date
3. Trigger state update via Bloc
4. Log action in `alert_log` to prevent duplicate notifications
| Item removed from or updated in inventory; alert cleared; confirmation shown

|===

**Detailed User Scenario (Mateo's Morning Alert):**
1. Mateo receives a push notification: "2 items expiring today or tomorrow"
2. Notification shows: "Milk (expires today)", "Yogurt (expires tomorrow)"
3. He taps the notification and the app opens and navigates to Alerts Center
4. He sees:
   - **Milk** | Expires: Today | Action: Consume Now / Discard
   - **Yogurt** | Expires: Tomorrow | Action: Consume Today / Extend to [date]
5. He taps "Consume Now" next to Milk and the item is marked consumed with quantity set to 0
6. For Yogurt, he taps "Extend" and the date picker appears; he extends it to 2 days out
7. Alerts list auto-refreshes; both items are now off the alert list

**Components Involved:**
- **Backend:** Supabase Cron Edge Function (TypeScript), Postgres triggers
- **Frontend Presentation:** Alerts Center screen, push notification handler
- **State Management:** Alert Cubit (if implemented) or real-time stream listener
- **Data Layer:** Alert repository, alert log data source
- **Domain:** `AutomatedCheckExpiration`, `AutomatedCheckStock` use cases
- **External:** Firebase Cloud Messaging (FCM), Apple Push Notification (APNs)

**Visual Evidence:**

=== Feature 3: Smart Grocery List Management (F-GL-AUTO + F-GL-USER)

**User Value:** Closes the inventory lifecycle loop. Auto-generates shopping lists based on inventory state, then enables quick shopping trip management (check off items, restock on return).

**Primary Users:** Shoppers, household managers

**End-to-End User Flow:**

.Grocery List Generation & Trip Management
[cols="2,3,2", options="header"]
|===
| **Input**
| **Processing**
| **Output**

| Automated daily check (from Feature 2) runs and identifies inventory gaps
Example: Milk quantity = 0, Bread expired 2 days ago, Pasta stock below threshold
| 1. Process AutoCheck output (items with status: OUT_OF_STOCK, EXPIRED, LOW_STOCK)
2. Apply priority order:
   - Priority 1: OUT_OF_STOCK items
   - Priority 2: EXPIRED items
   - Priority 3: LOW_STOCK items
   - Priority 4: Frequently used + low/out
3. Skip items already on active grocery list
4. Log auto-additions to `grocery_list_log`
| Grocery list auto-updated with prioritized items (e.g., Milk [OUT_OF_STOCK], Bread [EXPIRED])

| User navigates to "My Grocery List" screen
| App fetches active grocery list from Supabase; displays items grouped by category
Options shown:
- Checkbox to mark item as "in cart"
- Edit quantity / notes
- Remove item
- Add custom item (manual entry)
| Grocery list displayed with auto-generated items + any user-added custom items

| User is at supermarket; checks off items as they enter cart
Then, user completes shopping trip and taps "Finalize Grocery Run"
| 1. For each checked item:
   - Prompt for quantity bought (default = inventory gap amount)
   - Prompt for expiration date (if perishable)
2. Collect receipt info (optional: total spent, payment method)
3. Validate entries
| Dialog/form shown for final confirmation + quantity/expiration entry

| User confirms and taps "Save & Restock"
| 1. For each item, update/insert into Core Inventory with new quantities and expiration dates
2. Clear checked items from grocery list (or archive)
3. Log restocking action in `grocery_list_log`
4. Trigger inventory state update (Bloc)
| Updated inventory displayed in Core Inventory screen; grocery list cleared of checked items; confirmation message shown

|===

=== Implementation Decisions and Trade-offs

This subsection documents the major implementation decisions that shape the Milestone 3 Home Inventory system. The entries are written in a lightweight ADR style so reviewers can understand the selected approach, the alternatives considered, and the consequences of each decision. These decisions focus on major subsystem choices rather than minor implementation details.

Current implementation decisions are separated from planned or feature-dependent decisions where the runtime behavior is not fully implemented or depends on later integration work.

==== ADR-01: Use Flutter for the Mobile Client

**Status:** Accepted — M3 current

**Context / Problem:**

The system needs a mobile-first client that supports inventory capture, household coordination, alerts, grocery-list workflows, reporting screens, barcode scanning, and eventual push-notification handling. The application must support fast UI iteration during the milestone while remaining maintainable for feature teams working on separate screens and flows.

**Selected Option:**

Use **Flutter** with **Dart** as the mobile client framework. The client uses Material 3 UI components, GoRouter for navigation, and Bloc/Cubit for feature state management.

**Alternatives Considered:**

* Native Android and iOS applications using Kotlin/Swift.
* React Native.
* A web-first application with responsive mobile layout.

**Rationale:**

Flutter provides a single shared codebase for mobile UI development while still supporting native device features such as camera access, file handling, and push-notification integration. It also fits the current project structure because feature teams can implement screens, widgets, Cubits, routes, and domain/use-case logic in a consistent layered pattern.

**Trade-offs / Consequences:**

* Flutter reduces duplicate mobile development effort compared with separate native apps.
* Native platform behavior still requires platform-specific configuration for camera permissions, push notifications, builds, and signing.
* The team must maintain consistent state-management conventions to avoid disconnected feature implementations.
* Flutter is appropriate for the current milestone, but platform-specific edge cases may still require Android/iOS testing.

**Related Requirements / Constraints:**

Supports Core Inventory (`F-INV`), Alerts (`F-ALERT`), Grocery List (`F-GL-AUTO` / `F-GL-USER`), Reports (`F-SPEND`), barcode fallback capture, mobile-first usage, and reviewer-accessible local execution.

==== ADR-02: Use Supabase as the Backend Platform

**Status:** Accepted — M3 current

**Context / Problem:**

The system requires backend services for authentication, persistent inventory data, household/member data, shared synchronization, alert records, grocery-list data, reporting data, and future media storage. The team needs a backend approach that is quick to set up during the course milestone but still supports real application behavior.

**Selected Option:**

Use **Supabase** as the backend platform, including Supabase Auth, Supabase PostgreSQL, Supabase Realtime, PostgREST access through the Supabase Flutter SDK, and documented support for Supabase Storage and Edge Functions.

**Alternatives Considered:**

* Firebase Authentication, Firestore, Cloud Functions, and Firebase Storage.
* A custom REST API with Node.js/Express or similar backend framework.
* A local-only database with no hosted backend.
* Direct PostgreSQL hosting without Supabase platform services.

**Rationale:**

Supabase provides a PostgreSQL-backed platform with authentication, row-level authorization, realtime subscriptions, storage, and serverless function support in one stack. This reduces backend setup overhead and aligns with the project’s need for household-scoped data, shared inventory updates, and SQL-based relational modeling.

**Trade-offs / Consequences:**

* Supabase accelerates development by providing multiple backend services in one platform.
* The team becomes dependent on Supabase-specific configuration, SDK behavior, RLS policies, and hosted service availability.
* Direct SQL/Postgres modeling is stronger for relational data than document-only approaches, but it requires careful schema and policy design.
* Some current documentation still describes planned or feature-dependent Supabase services, so implementation status must remain explicit.

**Related Requirements / Constraints:**

Supports persistent inventory records, households, memberships, alert records, grocery-list records, reporting data, realtime collaboration, authentication, and authorization requirements such as household-scoped access control.

==== ADR-03: Enforce Access Control with Supabase Auth and Row Level Security

**Status:** Accepted — M3 current / policy configuration-dependent

**Context / Problem:**

Household inventory data must not be visible or modifiable by unauthorized users. Since the system supports shared households, members, roles, invitations, and potentially personal/shared inventory records, authorization cannot rely only on frontend checks.

**Selected Option:**

Use **Supabase Auth** for user identity and JWT sessions, and use **PostgreSQL Row Level Security (RLS)** policies as the database-level authorization boundary.

**Alternatives Considered:**

* Enforce authorization only in Flutter UI logic.
* Enforce authorization in a custom backend API layer.
* Use application-level role checks without database-level policies.
* Use separate databases or tables per household.

**Rationale:**

RLS places authorization close to the data. This is important because multiple client screens and feature modules may query shared backend tables. Supabase Auth provides the authenticated identity, while RLS policies can restrict queries and mutations based on user identity, household membership, and role relationships.

**Trade-offs / Consequences:**

* RLS reduces the risk of accidental data exposure from frontend mistakes.
* RLS policies must be tested carefully because incorrect policies can either block legitimate access or expose data.
* Debugging access issues can be harder than debugging ordinary frontend checks.
* Some sharing behavior is still marked as in progress, so role-based item visibility must not be presented as fully completed until policies and UI behavior are verified end-to-end.

**Related Requirements / Constraints:**

Supports household membership rules, invitation/membership state, shared inventory access, authentication, authorization, and protection of household-scoped data.

==== ADR-04: Store Current Inventory State Directly While Preserving Historical Meaning Separately

**Status:** Accepted — M3 current, with some audit/history behavior still evolving

**Context / Problem:**

The system needs to show current inventory quickly while also preserving enough history to explain changes, support alerts, avoid duplicate purchases, and avoid corrupting financial records when items are removed or archived.

**Selected Option:**

Store current inventory state directly in persistent inventory/stock records, including quantity, status, expiration data, item metadata, and household context. Treat quantity changes, alerts, grocery-list actions, and spending records as related historical or supporting records where implemented or documented.

**Alternatives Considered:**

* Compute current quantity only by replaying all historical transactions.
* Hard-delete items when they are consumed, discarded, or no longer tracked.
* Store only qualitative availability and avoid numeric quantity.
* Store all inventory behavior as unstructured notes or free-text logs.

**Rationale:**

Current inventory screens, reports, alerts, and grocery-list automation need fast access to the current item state. Keeping current state directly available makes UI updates and automated checks simpler. At the same time, the documentation preserves the rule that financial history and important records should not be silently deleted when inventory records are removed or archived.

**Trade-offs / Consequences:**

* Direct current-state storage is simpler and faster for the app.
* It can drift from reality if users forget to update quantities.
* Historical traceability requires disciplined logging or audit records; the current implementation and documentation should not imply complete audit coverage where it is not yet implemented.
* Soft deletion or archival is preferred over hard deletion when other records may still reference an item.

**Related Requirements / Constraints:**

Supports Core Inventory (`F-INV`), low-stock and out-of-stock checks, expiration status, dashboard/report generation, grocery restocking, non-negative quantity rules, and `DR-3` financial immutability.

==== ADR-05: Use Bloc/Cubit for Feature State Management

**Status:** Accepted — M3 current

**Context / Problem:**

The Flutter client needs predictable state handling for inventory loading, validation, success/error feedback, report views, alert interactions, grocery-list screens, and authentication-dependent routes.

**Selected Option:**

Use **flutter_bloc** with **Cubit** classes for feature-level state management.

**Alternatives Considered:**

* Local widget `setState` only.
* Provider.
* Riverpod.
* Redux-style global state management.
* Direct Supabase calls from UI widgets.

**Rationale:**

Cubit provides a lightweight state-management pattern that fits the project scale. It keeps UI widgets focused on rendering and user interaction while moving feature behavior into state classes, Cubits, use cases, and repositories. This supports clearer testing and avoids embedding backend calls directly into screens.

**Trade-offs / Consequences:**

* Cubit is simpler than full Bloc but still requires consistent separation between UI, state, domain, and data layers.
* Some simple screens may feel heavier than if they used only local widget state.
* If each feature team implements Cubits differently, documentation and onboarding can drift.
* Error/loading states must be modeled explicitly to avoid silent failures.

**Related Requirements / Constraints:**

Supports reliable UI behavior for Core Inventory, Reports, Alerts, Grocery List, authentication flow, error handling, and reviewer-verifiable feature behavior.

==== ADR-06: Use Supabase Realtime for Shared Inventory Synchronization

**Status:** Accepted — M3 current / feature-dependent

**Context / Problem:**

Shared household inventory loses value if users must manually refresh to see changes made by roommates. The system needs a synchronization approach that can keep inventory and household-facing views reasonably current across devices.

**Selected Option:**

Use **Supabase Realtime** subscriptions to receive PostgreSQL change events and update Flutter client state.

**Alternatives Considered:**

* Manual refresh only.
* Periodic polling from the client.
* Custom WebSocket server.
* Push notifications for every shared data change.

**Rationale:**

Supabase Realtime integrates with the selected backend stack and supports live updates without the team maintaining a custom synchronization server. It aligns with the shared-household use case where multiple users may add, edit, or consume items.

**Trade-offs / Consequences:**

* Realtime subscriptions reduce manual refresh needs.
* Realtime behavior depends on Supabase configuration, table replication settings, RLS policies, and client subscription handling.
* Realtime updates can create UI churn or race conditions if mutations also trigger full reloads.
* Offline conflict handling is still a separate concern and must not be treated as solved by Realtime alone.

**Related Requirements / Constraints:**

Supports shared inventory coordination, household visibility, reduced duplicate purchases, realtime list refresh, and synchronization-related implementation requirements.

==== ADR-07: Use Scheduled Backend Checks for Expiration and Stock Automation

**Status:** Accepted — documented / partially implemented

**Context / Problem:**

Low-stock, out-of-stock, near-expiry, and expired conditions should not depend entirely on users opening the app manually. The system needs a way to evaluate inventory conditions and produce alert or grocery-list outputs without constant user interaction.

**Selected Option:**

Use scheduled/backend automation through a cron-style trigger and hosted/Edge Function worker to evaluate stock and expiration conditions, deduplicate alerts, record run information, and create downstream alert or grocery-list outputs.

**Alternatives Considered:**

* Evaluate conditions only when the user opens the app.
* Evaluate conditions only after each item update.
* Use device-local background tasks only.
* Send alerts manually without automated checking.

**Rationale:**

Scheduled backend evaluation is more reliable than depending only on user behavior or local device background execution. It allows expiration and stock checks to run even when a user is not actively viewing the app. It also centralizes deduplication and run logging.

**Trade-offs / Consequences:**

* Backend automation improves reliability for reminders and grocery-list generation.
* It introduces operational complexity: scheduled triggers, function deployment, privileged database access, retries, logging, and failure recovery.
* Some behavior is documented or partially implemented, so the documentation must distinguish verified runtime behavior from planned automation design.
* Scheduled checks must avoid repeated alerts when no meaningful state transition has occurred.

**Related Requirements / Constraints:**

Supports `F-AUTOCHECK`, `F-ALERT`, expiration detection, low-stock detection, deduplication/anti-spam rules, grocery-list auto-generation, and scheduled sweep reliability requirements.

==== ADR-08: Separate Notification Records from Push Delivery

**Status:** Accepted — M3 current / push delivery setup-dependent

**Context / Problem:**

The system needs to represent alerts in a way that supports in-app review, deduplication, read/dismissed state, and possible push delivery. Push notification delivery may depend on platform setup, FCM/APNs configuration, and device permissions.

**Selected Option:**

Model alerts/notifications as persisted notification or alert records, while treating push delivery through FCM/APNs as a delivery mechanism rather than the source of truth.

**Alternatives Considered:**

* Use push notifications only with no persisted alert records.
* Use only in-app alerts with no push notification support.
* Store alert state only in local client memory.
* Send repeated push notifications directly from every automated check.

**Rationale:**

Persisted notification records support traceability, deduplication, read/unread handling, dismissal, and in-app review. Push delivery can then be added or configured as an additional channel without making the push provider the only place where alert state exists.

**Trade-offs / Consequences:**

* Separating records from delivery improves reliability and auditability.
* It requires additional schema and service logic for statuses such as unread, read, dismissed, or archived.
* Push delivery remains dependent on mobile platform configuration and permissions.
* The documentation must avoid implying that every alert record necessarily results in a delivered push notification.

**Related Requirements / Constraints:**

Supports actionable alert states, notification records, deduplication/anti-spam rules, Alerts Center behavior, expiration alerts, low-stock alerts, and future platform push delivery.

==== ADR-09: Use PNG Diagram Fallbacks with Source-Renderable Mermaid Files

**Status:** Accepted — M3 documentation current

**Context / Problem:**

The documentation needs diagrams that display reliably in GitHub and exported documents while also remaining editable by future developers. Mermaid source is useful for maintenance, but rendering support may differ across GitHub, AsciiDoc tooling, and exported formats.

**Selected Option:**

Store each diagram as both a rendered **PNG** and a source-renderable **Mermaid `.mmd`** file. Reference the PNG in `implementation.adoc` and include the source path for maintainability.

**Alternatives Considered:**

* Embed Mermaid directly only.
* Store only PNG files.
* Use PlantUML only.
* Use screenshots from an external diagramming tool with no source file.

**Rationale:**

PNG files render consistently in GitHub and exported documentation. Mermaid source files preserve the diagram logic and make future edits easier. This approach satisfies the documentation requirement for source-renderable diagrams while avoiding fragile rendering behavior.

**Trade-offs / Consequences:**

* Diagram changes require updating both the `.mmd` source and the PNG export.
* If the PNG and source diverge, reviewers may see inconsistent architecture or lifecycle information.
* The source path must be documented so future maintainers know where to update the diagram.

**Related Requirements / Constraints:**

Supports the diagram requirements for issue #647 and issue #648, Section 2.3 documentation readability, reviewer accessibility, and long-term maintainability.

==== Relationships and Ownership

The current implementation treats inventory as an owner-scoped aggregate. Each inventory belongs to one owner identifier, and each inventory contains a stock JSON map keyed by product id. A single inventory can therefore contain multiple stock entries, and each stock entry is associated with a product record.

At the model level, `StockEntity` and `StockModel` include an optional `ownerId`. This supports future ownership-aware behavior, but the current implementation does not yet fully enforce per-item visibility in the presentation layer. For that reason, ownership should be documented as partially implemented at the model/data level rather than as a completed UI access-control feature.

==== Persistence Strategy

The system uses Supabase as the persistence backend for the Core Inventory feature. Inventory data is currently stored as an owner-scoped inventory row containing a stock JSON map. The data source follows a fetch-modify-update pattern:

. Fetch the inventory row for the owner.
. Convert the stored stock JSON into `StockModel` objects.
. Add, replace, or remove the affected stock entry.
. Write the updated stock JSON map back to Supabase.
. Refresh the inventory state through `InventoryCubit`.

image::persistence-flow.png[Core Inventory Persistence Flow, width=100%]

This approach supports the implemented add, edit, delete, and lookup flows for Core Inventory. It also keeps persistence logic isolated in the data layer, consistent with the project’s Clean Architecture structure.

==== Implementation Notes and Changes

The current implementation replaces earlier placeholder data-model descriptions with the implemented owner-scoped persistence behavior. The main reconciliation points are:

* Inventory persistence is centered on an owner-scoped inventory aggregate.
* Stock entries are persisted inside a JSON map keyed by product id.
* `ownerId` exists in the stock model, but item-level visibility is not fully enforced in the UI.
* The current persistence layer does not create separate transaction or audit rows for every quantity change.
* Concurrent writes may overwrite intermediate changes because the current strategy uses fetch-modify-update without optimistic locking.

These limitations remain documented so the data model does not appear more complete than the implementation currently supports.
