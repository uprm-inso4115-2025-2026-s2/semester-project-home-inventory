= Build and Deployment Procedure

== Overview

This section documents the build, setup, and deployment procedure for the Digital Home Inventory system, so developers, reviewers, and team members can consistently set up and run the project from a clean environment without undocumented local configuration. The system uses a Flutter frontend with Supabase services for backend, authentication, storage, and synchronization.

== Repository Structure

The main repository contains project documentation under `docs/`, the Flutter application source under `src/`, and dependency management through `pubspec.yaml`. The Flutter client should always be executed from `src/`.

== Runtime Environment

The local development environment used during Milestone 3 includes Flutter SDK 3.35.5, Dart SDK 3.9.2, and package management through `flutter pub`. The authoritative dependency source for the Flutter client is:

----
src/pubspec.yaml
----

== Clone and Setup Procedure

=== 1. Clone the Repository

[source,bash]
----
git clone https://github.com/uprm-inso4115-2025-2026-s2/semester-project-home-inventory.git
cd semester-project-home-inventory
----

=== 2. Navigate to the Flutter Project

[source,bash]
----
cd src
----

=== 3. Install Dependencies

Download all dependencies defined in `pubspec.yaml`:

[source,bash]
----
flutter pub get
----

=== 4. Configure Environment Variables

For Milestone 3, the Supabase project URL and anonymous key are read directly from `src/lib/config/injection_dependencies.dart` inside the `Supabase.initialize(...)` call. No `.env` file, `--dart-define` flow, or external configuration loader is wired up yet, so a clean checkout connects to the team's shared Supabase project without extra setup.

[cols="2,3",options="header"]
|===
|Configuration value
|Source

|Supabase Project URL (`url:`)
|`src/lib/config/injection_dependencies.dart`

|Supabase Anonymous / Publishable Key (`anonKey:`)
|`src/lib/config/injection_dependencies.dart`
|===

To point the app at a different Supabase project (e.g., a personal sandbox), edit those two arguments in `injection_dependencies.dart` locally — do not commit replacement credentials. Planned for a later milestone: moving these values out of source into a git-ignored `.env` file or `--dart-define` build arguments (e.g. `flutter run --dart-define=SUPABASE_URL=... --dart-define=SUPABASE_ANON_KEY=...`); this section must be updated when that change lands. Once the project moves to per-developer or per-environment configuration, sensitive credentials and secrets must never be committed to version control.

=== 5. Check Flutter Environment

Verify the environment reports no critical dependency or SDK issues before running:

[source,bash]
----
flutter doctor
----

== Running the Application

Start an Android emulator, iOS simulator, or connect a physical device, then run (Flutter automatically builds and launches on the selected device):

[source,bash]
----
flutter run
----

=== iOS Build

iOS builds are produced via Xcode; see Known Limitations.

== Backend and External Services

The system depends on external services provided through Supabase: PostgreSQL database, Authentication, Realtime synchronization, Storage, and optional Edge Functions and automation services. Certain features may not function correctly without valid backend configuration and internet connectivity.

== Deployment Assumptions

For Milestone 3, deployment is treated as a local development and review workflow rather than a finalized production pipeline. Current assumptions: developers run the project locally using Flutter tooling; backend services are hosted through Supabase; environment-specific credentials are configured locally; and production hosting and release infrastructure may continue evolving in future milestones.

== Verification Procedure

After setup completes successfully:

* The Flutter project should compile without dependency errors.
* The application should launch successfully using `flutter run`.
* Supabase-connected features should initialize correctly when valid credentials are provided.
* Navigation, inventory management, alerts, and synchronization functionality should load without startup failures.
* A second team member or reviewer should be able to follow this procedure from a clean environment and successfully launch the application.

== Known Limitations

* Some functionality requires active internet connectivity.
* Push notification services may require additional platform configuration.
* Production deployment pipelines are not finalized.
* Certain features may behave differently depending on emulator/device permissions.
* iOS builds may require Apple-specific signing and provisioning configuration.

== Common Failure Modes and Recovery Steps

[cols="2,3",options="header"]
|===
|Issue
|Recovery Step

|`flutter pub get` fails
|Verify Flutter/Dart installation and internet connectivity, then rerun the command.

|Supabase connection errors
|Check that the Supabase URL and API keys are configured correctly.

|Application does not launch on emulator
|Restart the emulator/device and confirm Flutter detects it using `flutter devices`.

|Missing dependencies or SDK mismatch
|Verify the installed Flutter/Dart versions are compatible with the SDK constraint in `src/pubspec.yaml`.

|Permission-related barcode scanning failures
|Ensure camera permissions are enabled on the emulator or physical device.

|Build command fails
|Run `flutter clean` followed by `flutter pub get`, then retry the build command.
|===

== Security Considerations

* Never commit secrets, API keys, or private credentials.
* Store sensitive configuration outside version-controlled files.
* Use authenticated backend access through Supabase Auth.
* Limit access to environment configuration files when possible.
