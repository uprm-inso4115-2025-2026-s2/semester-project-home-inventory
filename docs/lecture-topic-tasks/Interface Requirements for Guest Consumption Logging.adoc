== Introduction

Guests or visitors have been previously identified as non-obvious stakeholders in issue #141. They can consume household inventory items like snacks, drinks, hand soap, napkins, toilet paper, etc. and have their consumption go unlogged, which in turn negatively affects inventory accuracy. In that previous analysis, it was considered that guests should be able to log their consumption via something like a QR code, granting them temporary guest mode access without obtaining full inventory management privileges. This document applies the requirements engineering framework from the Chapter 20: Requirements Acquisition lecture slides, specifically the Interface Requirements facet, to identify and compare interface options for guest consumption logging. For each option, the following are specified:

- Man-machine dialogue (sequence of interactions)
- Physiological interface (physical actions required)
- Shared data initialization (data needed before first use)
- Shared data refreshment (how the interface stays updated)

== Interface Option 1: QR Code Guest Logging

=== Description

The household member provides a QR code that guests can use to log their consumption. This can be achieved either by the household member pulling it up on their device and holding it out for guests to scan on their device or by printing it and putting it in a visible location (e.g., on the refrigerator, near the snack drawer, or on a whiteboard in the kitchen). Guests scan the QR code with their smartphone camera, which opens a lightweight web page where they can log consumption without creating an account or downloading the app.

=== Man-Machine Dialogue

|===
| Step | Actor | Action | System Response
| 1 | Guest | Opens camera app and scans QR code | Opens guest logging webpage
| 2 | Guest | Views list of common household items | Displays items (categorized or searchable)
| 3 | Guest | Selects an item consumed | Shows quantity options (e.g., "1", "2", "Half", "All")
| 4 | Guest | Confirms selection | Logs consumption, updates inventory, shows confirmation message ("Thanks for logging!")
| 5 | Guest | May repeat steps 2-4 for additional items | Each selection logged immediately
| 6 | Guest | Closes browser tab | Session ends automatically
|===

=== Physiological Interface

|===
| Action | Description
| Phone handling | Guest retrieves phone, opens camera app
| Visual scanning | Guest positions phone to scan QR code
| Tapping | Guest taps screen to select items and quantities
| Reading | Guest reads item names and confirmation messages
|===

=== Shared Data Initialization

- QR code must be generated and provided or printed out by a household member
- QR code must encode a URL pointing to the guest logging endpoint (e.g., `https://app.example.com/guest/household123`)
- QR code must include a secure, time-limited token or household identifier
- Initial item list must be populated from the household's existing inventory
- Guest logging endpoint must be configured to accept anonymous POST requests (rate-limited)

=== Shared Data Refreshment

- Item list is fetched from the database each time the guest page loads (real-time)
- If household members add new items while guest page is open, items are not automatically shown unless the page is refreshed
- Consumption counts are immediately reflected in the household inventory (real-time)
- QR code remains valid indefinitely or until regenerated by household member
- Session tokens can have expiration (e.g., 24 hours) for security

=== Risks

|===
| Risk | Likelihood | Mitigation
| QR code photographed and shared outside household | Possible | Regenerate QR code periodically; use time-limited tokens
| Guest accidentally logs wrong item | Possible | Provide "undo" or "report mistake" option
| Guest logs maliciously (e.g., logging items not consumed) | Unlikely | Rate limiting; admin can review logs; low-stakes environment
| No internet access on guest's phone | Possible | Fallback to SMS option (Option 2) if household wifi cannot be provided to the guest
|===

== Interface Option 2: SMS/Text Message Logging

=== Description

A phone number is designated for the household (e.g., a Google Voice number or a dedicated SMS service). Guests send a text message to that number with a simple command (e.g., "milk 1" to log one milk consumed). No app installation or account creation is required.

=== Man-Machine Dialogue

|===
| Step | Actor | Action | System Response
| 1 | Guest | Opens SMS app on phone | N/A
| 2 | Guest | Composes message to household number with format: `ITEM QUANTITY` (e.g., "milk 1") | N/A
| 3 | Guest | Sends message | System parses message, logs consumption, sends confirmation reply ("Logged: 1 milk")
| 4 | Guest | If format is incorrect | System replies with help message: "Text 'ITEM QUANTITY' (e.g., 'milk 1')"
| 5 | Guest | May send additional messages for other items | Each message logged individually
|===

=== Physiological Interface

|===
| Action | Description
| Phone handling | Guest retrieves phone, opens SMS app
| Typing | Guest types command using keyboard
| Reading | Guest reads confirmation or help messages
| Sending | Guest presses send button
|===

=== Shared Data Initialization

- Dedicated phone number must be provisioned (e.g., Twilio, Google Voice, or carrier SMS gateway)
- SMS service must be configured to forward messages to the application's backend
- Backend must include an SMS parser that maps keywords to item names in the household inventory
- Initial keyword-to-item mapping must be defined (e.g., "milk" -> Milk, "tp" -> Toilet Paper)
- Household members must be notified of the SMS number and command format

=== Shared Data Refreshment

- Keyword-to-item mapping can be updated by household members as new items are added
- SMS service runs continuously; no "refresh" needed by guests
- Consumption logs are immediately reflected in inventory
- Confirmation messages are sent in real-time

=== Risks

|===
| Risk | Likelihood | Mitigation
| SMS costs (per message) | Certain | Use low-cost provider; household pays small fee; limit to reasonable monthly messages
| Guest types wrong command | Likely | Provide help message; support common variations
| SMS delivery delay | Possible | Use reliable provider; confirm message with "Logged" reply
| Phone number privacy concerns | Low | Use dedicated number not linked to personal numbers
| Guest does not know command format | Likely | Message the number to get a help message with instructions; help command
|===

== Comparison of Options

[cols="1,2,2,2", options="header"]
|===
| Criteria | QR Code Logging | SMS Logging | Winner
| Ease of use (guest friction) | Scan → tap → done (2-3 steps) | Open SMS → type → send (3-4 steps, requires typing) | QR Code
| Accessibility | Requires smartphone with camera; visual interface | Requires any phone with SMS; works on basic phones | SMS (more accessible)
| Security | Time-limited tokens; rate limiting; no account needed | Phone number known; rate limiting | QR Code (slightly better)
| Implementation complexity | Moderate (web page, QR generation, token management) | Moderate (SMS gateway integration, parser) | Tie
| Maintenance overhead | Low (QR codes static; page updates automatically) | Low (keyword mapping may need updates) | QR Code
| Guest learning curve | Minimal (scan and tap) | Low (must learn command format) | QR Code
| Offline capability | Requires internet on guest phone | Requires cellular/SMS service | Tie
| Cost | No per-use cost | Per-message cost | QR Code
|===

== Recommended Option

**Recommendation: QR Code Guest Logging**

The QR code option is recommended as the primary guest logging interface for the following reasons:

1. **Lower guest friction:** Scanning a QR code and tapping items requires minimal effort and no typing, making guests more likely to actually log consumption.

2. **No per-use cost:** Unlike SMS, there are no variable costs associated with each guest log.

3. **Richer interface:** Guests can see available items, select quantities, and receive visual confirmation—reducing errors.

4. **Better user experience:** The interface can show categories, search, and provide immediate feedback.

5. **Aligns with stakeholder analysis:** The previous non-obvious stakeholder analysis (issue #141) specifically mentioned QR codes as a potential solution.

**When to use SMS as fallback:**

SMS logging could be implemented as a secondary option for:
- Guests without smartphones (or with broken cameras)
- Situations with poor internet connectivity
- Households with high guest volume where SMS costs are negligible

**Implementation Priority:**
1. Implement QR code logging as primary interface
2. Add SMS logging as optional fallback (if budget allows)

== Summary of Requirements

Based on the analysis, the following requirements are derived for the guest logging interface:

|===
| ID | Requirement | Source
| REQ-GUEST-01 | The system shall provide a QR code that guests can scan to access a lightweight consumption logging page | QR Option
| REQ-GUEST-02 | The guest logging page shall display the household's current inventory items for selection | QR Option
| REQ-GUEST-03 | The guest logging page shall require no account creation or login | QR Option
| REQ-GUEST-04 | The guest logging page shall provide confirmation after successful log | QR Option
| REQ-GUEST-05 | The system shall rate-limit guest log requests to prevent abuse | Both
| REQ-GUEST-06 | Guest logs shall be immediately reflected in the household inventory | Both
| REQ-GUEST-07 | Household members shall be able to regenerate the QR code for security | QR Option
| REQ-GUEST-08 | The guest logging interface shall not allow guests to view or modify non-inventory data | Both
|===
